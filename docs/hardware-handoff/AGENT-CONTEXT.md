## Mission

Implement ESP32-S3 firmware that conforms to the existing BMO voice MVP backend. Do not redesign the backend protocol.

1. Public hardware ↔ backend protocol: [`../hardware-contract/BMO-MVP-HW-INTERFACE-CONTRACT-v1.0.5.md`](../hardware-contract/BMO-MVP-HW-INTERFACE-CONTRACT-v1.0.5.md).

## Required firmware behavior

```text
boot
→ Wi-Fi
→ WSS connect
→ authenticate
→ idle
→ local wake word
→ local WAV recording while display remains idle
→ UUID v4
→ raw HTTP WAV upload
→ thinking
→ audio_ready
→ HTTP MP3 download
→ speaking when playback begins
→ playback finishes
→ idle/cleanup + audio_playback_done completion action
```

## Only valid event names

ESP32 → backend:

```text
authenticate
audio_playback_done
audio_playback_failed
```

Backend → ESP32:

```text
authenticated
authentication_failed
connection_replaced
display_status
audio_ready
request_failed
```

Never invent `audio_chunk`, `wake_word_detected`, `ack`, `audio_ready_received`, or a `listening` display mode.

## Non-obvious requirements that must not be missed

- HTTP upload body is raw WAV, not multipart.
- WebSocket must be authenticated before upload.
- Request ID is UUID v4 generated by firmware.
- Retry of the same recording reuses the same request ID and same WAV bytes.
- HTTP `202` and WebSocket `thinking` can arrive in either order.
- One active request per device.
- Backend only commands display `thinking`; firmware owns `idle`, `speaking`, and `error`.
- `speaking` begins when playback actually starts, not when `audio_ready` arrives.
- MP3 URL has finite TTL.
- Duplicate `audio_ready` after reconnect must never cause double playback.
- There is no `audio_ready_received` event.
- MP3 download retry is once from byte 0; no Range/resume requirement.
- Playback result event can be resent after reconnect; backend handles it idempotently.
- Backend voice request state is in memory. Backend restart may return `backend_state: idle`; firmware must clear stale local request.
- Local firmware must contain error audio so failures still have feedback when backend/TTS is unavailable.
- Production uses HTTPS/WSS and firmware must validate TLS certificates. Connect by the verified hostname, not the VPS IP, so DNS migration and TLS/SNI keep working.
- A newer authenticated connection for the same device replaces the older connection; handle `connection_replaced` cleanly and do not create a reconnect storm from the superseded socket.
- There is no one-hour/application-level idle timeout while native ping/pong remains healthy; keep the authenticated socket alive.

## Required local request state

At minimum:

```text
current_request_id
playback_state = waiting | downloading | playing | done_pending_send | failed_pending_send
```

## Do not assume RVC availability

Backend output contract is MP3 regardless of whether RVC was successfully applied. Firmware must not branch on RVC state.

P8 production uses Piper Prudence primary with Kokoro fallback and
`RVC_ENABLED=false`; real RVC inference remains archived/unverified and is not
a production dependency. This is a backend concern, not a firmware protocol
change.

## Definition of done

Do not declare firmware integration complete just because happy path works. Execute [`ACCEPTANCE-TESTS.md`](ACCEPTANCE-TESTS.md), including reconnect, duplicate, expiry, invalid audio, no-speech, and playback failure cases.


## Production TLS prerequisite

Before connecting to the verified production HTTPS/WSS endpoint, firmware must synchronize a trustworthy clock (normally NTP/SNTP) and validate the server certificate chain. Do not pin a short-lived leaf certificate unless deployment documentation explicitly requires it; do not disable TLS verification.
