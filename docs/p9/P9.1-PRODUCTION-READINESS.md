## Narrow health fix

Source tracing proved that Audio treated `rvc_available=false` as degraded even
when `Settings.rvc_enabled=false`, and Backend then propagated that optional
condition into the public `status` field. The fix in commit `bf5a0fc`:

1. Audio requires RVC only when the RVC-enabled setting is true.
2. Disabled/absent RVC returns Audio `status=ok` while retaining
   `rvc_available=false` as truthful capability information.
3. Enabled-but-unavailable RVC returns Audio `status=degraded`.
4. Backend accepts only Audio `status=ok` as ready; enabled RVC failure becomes
   Backend HTTP `503`/`status=error`.
5. Required STT, Piper, Kokoro, and FFmpeg failures still fail readiness.
6. No RVC retry, process, model, endpoint, voice event, or Hardware Contract
   behavior was added.

Focused regression results: Audio `17/17`; Backend health/readiness `11/11`.
The existing public `/health` status expectation is unchanged in production
until a separately authorized deployment.
