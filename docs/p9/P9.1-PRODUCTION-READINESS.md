## Scope and authority

This package documents the production topology, operator decisions, key and
backup lifecycle, canary, rollback, observability, and future acceptance gates
for P9.1. It does not install PostgreSQL, run a migration, change production
Compose/Caddy/DNS/TLS/UFW/Tailscale, deploy an image, or expose P9.1 APIs.

The decision statuses used throughout the package are:

- `LOCKED_BY_EXISTING_ARCHITECTURE` — must remain unchanged.
- `TECHNICAL_DECISION_AUTHORIZED` — finalized as a P9.1 implementation or
  runbook detail without selecting a product, vendor, account, or owner.
- `OPERATOR_APPROVAL_REQUIRED` — recommendation only; the operator must select
  or own the external account, key, paid service, alert target, or rollout.
- `BLOCKER` — a safe canary cannot proceed until the item is resolved.

## Narrow health fix

Source tracing proved that Audio treated `rvc_available=false` as degraded even
when `Settings.rvc_enabled=false`, and Backend then propagated that optional
condition into the public `status` field. The fix in commit `bf5a0fc`:

1. Audio requires RVC only when the RVC-enabled setting is true.
2. Disabled/absent RVC returns Audio `status=ok` while retaining
   `rvc_available=false` as truthful capability information.
3. Enabled-but-unavailable RVC returns Audio `status=degraded`.
4. Backend accepts only Audio `status=ok` as ready; enabled RVC failure becomes
   Backend HTTP `503`/`status=error`.
5. Required STT, Piper, Kokoro, and FFmpeg failures still fail readiness.
6. No RVC retry, process, model, endpoint, voice event, or Hardware Contract
   behavior was added.

Focused regression results: Audio `17/17`; Backend health/readiness `11/11`.
The existing public `/health` status expectation is unchanged in production
until a separately authorized deployment.

## Production gates

The following must be closed in a later, separately authorized canary task:

- Windows operator-PC path/SSH-ACL check, real transfer, checksum/GPG
  verification, and exact-copy restore rehearsal;
- provisioning-time secret UID/GID/mode checks, read-only mount checks, startup
  failure checks, and rotation rehearsals;
- backup scheduler activation, manual-pull verification, and alert destination;
- first-canary verification of the locked Caddy/trusted-proxy topology;
- explicit kernel-OOM baseline immediately before canary;
- hardware-authenticated pairing binding, or a deliberate pairing-disabled flag;
- production migration approval, image build from final main, canary approval,
  soak, and rollback criteria.

These are not claims that disaster recovery or production readiness is
complete. Local encrypted backup and isolated restore are verified; disaster
recovery remains incomplete until the approved personal-computer copy is
transferred and restored successfully. Weekly manual transfer creates an
approximately seven-day worst-case disaster-recovery RPO.

Secret ownership and injection are approved design decisions, not evidence
that secrets are provisioned or active. Production PostgreSQL is not installed,
no production migration has occurred, RVC remains disabled, and P9.2–P9.6
remain unimplemented.
