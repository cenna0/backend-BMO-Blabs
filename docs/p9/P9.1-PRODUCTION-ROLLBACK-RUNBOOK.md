# P9.1 Production Rollback Runbook

Status: proposed; no rollback command is executed by this branch. Preserve the
current P8 Backend, Audio, and Hermes image/configuration until the future
operator-approved canary is complete.

## Universal first actions

1. Announce the incident privately and stop the canary.
2. Capture timestamps, image digests, Git SHA, health payloads, restart/OOM
   state, logs with redaction, and database/migration status.
3. Disable P9.1 flags if the application remains responsive.
4. Restore the last known-good Backend image/configuration and verify the
   existing public `/health=200`, `/livez=404`, `/readyz=404` contract.
5. Do not touch Audio, the active Audio digest, the P7 rollback digest, or the
   Hardware Contract.

## Decision matrix

| Failure | Detection and immediate action | Database/credential action | Retry gate |
|---|---|---|---|
| PostgreSQL before migration | health timeout; stop DB candidate | remove only isolated candidate data after evidence; no production data loss | fresh isolated rehearsal |
| Migration fails | nonzero `migrate deploy` or failed history row; stop app | preserve DB; inspect locks/error; corrective forward migration or fresh restore | reviewed SQL and empty-db rerun |
| Migration succeeds, candidate fails | private health/test failure | retain schema; roll back app image, no down migration | compatibility proof |
| Parallel canary fails | any private acceptance failure | isolate candidate DB; revoke test sessions/invites | root cause and rerun |
| Replacement fails before public traffic | startup/health failure | restore prior app config; keep DB for inspection | private canary pass |
| Public health fails | 5xx or wrong 200/404/404; stop traffic | app rollback; do not reset DB | two clean health windows |
| Legacy voice/WebSocket regresses | endpoint/status/audio regression | app rollback; Audio/Hermes unchanged | full legacy regression |
| Auth/session defect | enumeration, rotation, logout, or replay failure | disable P9 auth flags; revoke affected sessions; rotate key if exposed | security review |
| Pairing defect | wrong owner, race, replay, or code leak | disable pairing; revoke device sessions and HMAC key if compromise | hardware-bound test pass |
| Rate-limit identity defect | spoofed header changes bucket or bypasses limit | disable affected route; retain logs redacted | proxy/header test pass |
| Host memory unsafe | MemAvailable below threshold or cgroup >85% sustained | stop canary and backup/restore workload; app rollback | resource retest |
| Kernel OOM increases | `/proc/vmstat` delta >0 | stop all candidate work; restore prior app; preserve evidence | new baseline and root cause |
| Local backup fails | dump/checksum/encryption/retention failure | do not delete last valid backup; stop cleanup | successful isolated retry |
| Off-VPS upload fails | remote missing/checksum mismatch | retain local encrypted artifact; alert operator; no false DR claim | approved remote verification |
| Restore fails | wrong row counts, relationships, key, or app query | quarantine target; never overwrite source | fresh target and corrected key |
| Monitoring fails | missing private signals/alerts | do not proceed with replacement; keep current app | monitoring acceptance pass |
| Secret suspected compromised | redacted evidence or unauthorized access | disable/revoke, rotate with overlap where safe, revoke sessions, preserve audit | owner-approved incident closure |

## Migration and database handling

Rolling back the application after a successful P9.1 migration is preferred.
Keep PostgreSQL data and `_prisma_migrations` intact. Do not delete a live data
directory, reset the schema, or run a blind down migration. If the old Backend
cannot start against the new schema, keep the database private and restore the
last known-good application plus a reviewed compatibility/corrective migration
or an isolated verified database restore.

## Credential compromise

JWT rotation must overlap old and new verification only for the documented
15-minute access-token window; then reject the old key and revoke sessions as
needed. Pairing HMAC compromise requires disabling pairing, invalidating active
codes, rotating the key, and re-provisioning device credentials. Database
credential compromise requires revoking the affected role, rotating it from a
secret file, recycling connections, and checking audit/access evidence.

## Re-entry criteria

Another attempt is prohibited until the failure has a written root cause,
evidence is retained, the relevant regression is added, the production health
comparison remains unchanged, and an operator approves the revised gate.
