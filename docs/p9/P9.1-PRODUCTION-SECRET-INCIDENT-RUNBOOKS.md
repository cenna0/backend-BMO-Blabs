# P9.1 Production Secret Incident Runbooks

**Status:** future operator procedure; no incident command is executed by this
readiness branch. Preserve sanitized timestamps, source/image identity, audit
IDs, service status, and outcome codes. Never preserve a secret value in the
incident record.

## Common incident rules

1. Treat suspicion as exposure until disproven.
2. Stop the affected P9.1 feature or one-shot job and keep public voice
   services untouched unless the incident affects the Backend process itself.
3. Disable the smallest relevant feature flag: authentication, pairing,
   invitation registration, or backup/restore.
4. Preserve sanitized logs and access timestamps; do not capture process
   environments, command lines containing values, database rows, or tokens.
5. Rotate the affected secret, revoke dependent sessions/codes/roles, and
   validate the replacement in a private boundary.
6. Re-enable only after the relevant acceptance checks and operator approval.
7. Update the decision register and incident record with version identifiers,
   not secret values.

## JWT signing key suspected compromised

- **Detection:** key appears in logs, image/config output, a ticket, an
  unauthorized file, or unexplained token-signature activity.
- **Immediate containment:** disable P9 authentication flags and stop new auth
  traffic; preserve current Backend evidence.
- **Features to disable:** login, registration, refresh, and protected P9 APIs.
- **Credentials to rotate:** JWT key first; rotate any co-exposed app or host
  credential. Do not rotate unrelated Audio/Hermes credentials automatically.
- **Sessions/codes:** revoke all refresh sessions and active pairing codes;
  revoke device-bound sessions where applicable.
- **Database action:** preserve audit evidence; use the app role only through
  the approved private procedure; no schema reset.
- **Backup implication:** take no backup containing the exposed key; verify
  the backup encryption boundary separately.
- **Evidence:** key version, token failure counts, audit IDs, timestamps,
  process/image identity, and sanitized exposure location.
- **Rollback:** never restore the suspected key. Roll back only to a trusted
  application configuration that uses the replacement key.
- **Re-enable:** validate new login, protected request, old-token rejection,
  refresh rotation, logout, and redacted logs.
- **User impact:** active sessions require reauthentication; explain only the
  minimum necessary operational impact.
- **Documentation:** record the compromise, v2 activation, revocation scope,
  recovery-copy update, and final acceptance results.

## Pairing HMAC key suspected compromised

- **Detection:** key exposure, pairing-code guesses succeeding unexpectedly,
  unexplained pairing failures, or code material in logs.
- **Immediate containment:** disable pairing issuance and claims; preserve audit
  records without codes.
- **Features to disable:** all pairing issue/claim/status flows, while auth and
  voice remain available if independently healthy.
- **Credentials to rotate:** pairing HMAC key and any co-exposed hardware
  bootstrap credential.
- **Sessions/codes:** revoke all `ISSUED` pairing codes and device-bound
  sessions where applicable; do not silently unpair every device unless the
  incident scope requires it.
- **Database action:** preserve ownership rows and audit events; no broad
  deletion.
- **Backup implication:** backup the sanitized state only; do not place the
  HMAC key in a database backup or transfer artifact.
- **Evidence:** event IDs, device identity references where safe, timestamps,
  attempt counts, and sanitized outcome codes.
- **Rollback:** do not restore the suspected key; use the new key and keep
  pairing disabled until physical-device authentication is revalidated.
- **Re-enable:** verify old claims fail, new ten-minute codes work, races and
  replay fail, and no code appears in logs.
- **User impact:** pairing is temporarily unavailable; existing ownership is
  preserved unless explicit revocation is required.
- **Documentation:** record key version, invalidation time, hardware gate, and
  operator approval.

## PostgreSQL application credential suspected compromised

- **Detection:** credential in logs/config, unexpected database source, or
  privilege-use anomaly.
- **Immediate containment:** disable P9.1 public flags or isolate Backend;
  keep Audio/Hermes unchanged.
- **Features to disable:** database-backed P9 APIs and, if necessary, the
  Backend candidate; public legacy voice rollback follows the main rollback
  runbook if Backend integrity is uncertain.
- **Credentials to rotate:** app role, and any co-exposed database values;
  never expose owner/migration credentials to Backend.
- **Sessions/codes:** revoke refresh sessions if unauthorized data access is
  plausible; revoke pairing codes only if device data may be affected.
- **Database action:** inspect role access, revoke/replace the role, drain
  connections, and preserve audit evidence; do not reset schema.
- **Backup implication:** verify backup role and encryption material are
  separate; do not use the app credential for `pg_dump`.
- **Evidence:** role identifier, connection times, database error classes,
  migration state, and sanitized audit IDs.
- **Rollback:** restore the previous trusted Backend only after it is given a
  newly validated app credential; keep the database private.
- **Re-enable:** verify least privilege, fresh Prisma connection, ownership
  isolation, login, `/me`, and no credential leakage.
- **User impact:** P9.1 operations may be paused; legacy voice remains a
  separate rollback decision.
- **Documentation:** record role rotation and connection-drain evidence.

## PostgreSQL owner or migration credential suspected compromised

- **Detection:** value exposure, unauthorized DDL/role activity, unexpected
  migration history, or access outside the approved window.
- **Immediate containment:** stop migration/bootstrap/restore jobs and keep
  the database private; disable P9.1 public flags.
- **Features to disable:** all schema-changing and administrative operations;
  normal Backend may remain stopped until scope is understood.
- **Credentials to rotate:** affected owner/migration credential; review app,
  backup, and restore credentials for co-exposure.
- **Sessions/codes:** revoke sessions if application data may have been read or
  changed; invalidate pairing codes if device data may be affected.
- **Database action:** preserve the data directory and migration table, inspect
  DDL/role audit evidence, and use forward correction or verified restore.
- **Backup implication:** do not overwrite the last known-good encrypted
  backup; verify its checksum and key independently.
- **Evidence:** migration IDs, SQL outcome, role events, locks, timestamps, and
  database checksum/state evidence without rows or passwords.
- **Rollback:** no blind down migration and no destructive reset; restore the
  application or an isolated verified database as directed by the rollback
  runbook.
- **Re-enable:** reviewed SQL, empty-database rerun, role-privilege checks,
  persistence, and restore acceptance must pass.
- **User impact:** P9.1 unavailable until schema integrity is established.
- **Documentation:** record the migration/credential incident and corrective
  forward action.

## Backup encryption material suspected compromised

- **Detection:** key in an unauthorized location, decrypt failure anomaly, or
  unauthorized readable backup artifact.
- **Immediate containment:** stop backup and restore jobs; retain the newest
  valid local encrypted artifact; do not delete evidence.
- **Features to disable:** automated backup success reporting, manual restore,
  and off-VPS transfer until the new key is verified.
- **Credentials to rotate:** backup encryption material and any co-exposed
  backup-role credential.
- **Sessions/codes:** none by default; revoke sessions only if the exposure
  also contained auth material.
- **Database action:** no schema mutation; use the existing private database
  only to create a reviewed replacement backup.
- **Backup implication:** treat all artifacts encrypted with the exposed
  symmetric key as potentially readable; create a v2 set and update PC/offline
  copies.
- **Evidence:** artifact names/checksums, key versions, restore outcomes, and
  exposure timestamps without key fingerprints.
- **Rollback:** never return to the suspected key. Keep old artifacts only if
  their confidentiality risk is accepted and the key remains needed for
  controlled migration to v2.
- **Re-enable:** checksum, encryption, wrong-key rejection, exact PC-copy
  restore, and retention checks.
- **User impact:** backup/restore may be paused; no false disaster-recovery
  claim is allowed.
- **Documentation:** update recovery inventory and key version records.

## Operator SSH or deployment access suspected compromised

- **Detection:** unexpected host login, changed access policy, unknown command,
  or lost operator device.
- **Immediate containment:** revoke the affected host access path and stop all
  P9.1 maintenance operations; do not destroy evidence.
- **Features to disable:** pending P9.1 deployment, migration, backup pull,
  and restore operations.
- **Credentials to rotate:** SSH/Tailscale/deploy access and any P9 secret that
  may have been readable from the host.
- **Sessions/codes:** revoke P9 sessions and pairing codes if host exposure
  could reach Backend or database secrets.
- **Database action:** inspect access evidence and rotate app/admin roles if
  accessible; do not run unreviewed cleanup commands.
- **Backup implication:** assume local artifacts and mounted key material may
  have been exposed; rotate backup key and verify PC/offline copies.
- **Evidence:** host authentication timestamps, source addresses, changed-file
  records, and service state without command secrets.
- **Rollback:** preserve the current P8 runtime; no canary until host access
  is re-established and re-audited.
- **Re-enable:** operator-owned access, least privilege, file modes, and all
  P9 secret isolation checks pass.
- **User impact:** maintenance and P9.1 access may be paused.
- **Documentation:** update access ownership and incident records.

## Invitation secret suspected exposed

- **Detection:** raw invitation appears in a log, ticket, screenshot, history,
  or an unintended person’s view.
- **Immediate containment:** revoke that invitation immediately.
- **Features to disable:** no global feature needs disabling unless the
  operator workflow itself is compromised.
- **Credentials to rotate:** none globally; rotate host/operator access if the
  exposure came from that boundary.
- **Sessions/codes:** revoke any session created with the invitation if the
  intended recipient is not trusted.
- **Database action:** verify one-use state, expiry, hash-only persistence, and
  audit event; do not search for the raw value.
- **Backup implication:** ensure raw value is absent from backup/evidence; the
  invitation hash may remain in database backup.
- **Evidence:** invitation ID, event ID, expiry, and outcome only.
- **Rollback:** no code rollback; create a new invitation only through the
  operator command after containment.
- **Re-enable:** generic registration failures, one-use atomicity, and audit
  redaction pass.
- **User impact:** the intended invitee receives a replacement through the
  approved secure channel.
- **Documentation:** record revocation without recording the secret.

## Manual off-VPS backup copy suspected exposed

- **Detection:** PC loss, unauthorized PC access, plaintext found beside an
  artifact, checksum mismatch, or unknown copy.
- **Immediate containment:** stop treating that copy as trusted; preserve the
  checksum/manifest and do not upload it elsewhere.
- **Features to disable:** restore from that copy and any transfer workflow
  using it.
- **Credentials to rotate:** backup encryption material if the key or a
  decryptable plaintext was exposed; rotate operator-PC/host access.
- **Sessions/codes:** none unless the copy included application secrets; if it
  did, follow the relevant JWT/database/pairing incident procedure.
- **Database action:** no mutation; validate a fresh encrypted artifact from
  the private VPS and preserve the last good copy.
- **Backup implication:** verify the PC artifact, checksum, manifest, and
  encryption; replace the PC recovery set and additional offline copy.
- **Evidence:** artifact name/checksum, manifest identity, copy location class,
  and verification result without database contents.
- **Rollback:** no restore from the suspect copy; use a separately verified
  artifact or stop recovery.
- **Re-enable:** exact-copy restore from a newly verified PC/offline artifact
  passes application checks.
- **User impact:** disaster recovery may be temporarily unavailable; state the
  RPO honestly.
- **Documentation:** update the recovery inventory and manual-transfer record.
