# P9.1 Trusted Proxy and Rate Limiting

## Observed topology

```text
Public client → Caddy TLS edge → loopback Backend :3000
                                  ├─ loopback Audio :8001
                                  └─ loopback Hermes :8642
```

The current production Backend uses host networking and listens on
`127.0.0.1:3000`. The readable deployment template does not expose PostgreSQL.
The active `/etc/caddy/Caddyfile` was not readable by the audit account; the
operator must validate the active Caddy configuration before a canary. Public
probes and listener inspection confirm the external route and loopback origins,
but do not replace that configuration review.

## Verdict

The candidate currently leaves Express `trust proxy` at its safe default
`false`. This prevents arbitrary forwarded headers from controlling identity,
but all public requests arriving from loopback Caddy can share one limiter key.
It is not the final production rate-limit design.

Recommended future production configuration, only after the exact Caddy edge is
approved:

```ts
app.set("trust proxy", (ip: string) =>
  ip === "127.0.0.1" ||
  ip === "::1" ||
  ip === "::ffff:127.0.0.1"
);
```

This trusts only the loopback hop, not `true`, a hop count, a public CIDR, or
arbitrary client headers. Caddy must be the first public proxy and must use its
default behavior of ignoring incoming `X-Forwarded-*` values when constructing
the upstream headers. Caddy's documentation explicitly describes this
anti-spoofing default; do not add a CDN or another proxy without a new trusted
CIDR decision. See [Caddy reverse_proxy forwarded-header behavior](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)
and [Express proxy guidance](https://expressjs.com/en/guide/behind-proxies.html).

This is `OPERATOR_APPROVAL_REQUIRED` because it depends on the active Caddy
path and deployment edge. No Caddy or Backend runtime configuration is changed
by this branch.

## Limiter policy

| Route class | Limit | Key | Response |
|---|---:|---|---|
| Registration | 5 / 15 min | canonical client IP + normalized email | `429 {"error":"RATE_LIMITED"}` |
| Login | 5 / 15 min | canonical client IP + normalized email | generic `429`; no account existence |
| Refresh | 20 / 15 min | canonical client IP | generic `429`; rotation/replay still executes server-side |
| Pairing issue/claim | 10 / 15 min | canonical client IP plus authenticated user where available | generic `429`; no code/pairing enumeration |

Use `express-rate-limit@8.6.1` with an explicit IPv6 subnet policy (recommend
`ipv6Subnet: 56`) and no custom header-based key. Normalize IPv4-mapped IPv6
values to the same canonical IPv4 representation before any composite key.
The limiter must not use `X-Forwarded-For`, `X-Real-IP`, `Forwarded`, email,
device ID, pairing ID, or Authorization text as a standalone trust signal.

The limiter is intentionally single-instance in-memory. It resets on Backend
restart and does not coordinate parallel instances. No Redis is added. During
the future canary only one Backend instance may receive the candidate traffic;
the reset limitation must be monitored and documented.

## Header and direct-access tests

Run these in an isolated server before the canary; do not send spoofed tests to
production:

1. Through a Caddy-equivalent trusted loopback request, send an attacker-supplied
   `X-Forwarded-For`; Caddy must overwrite it and the Backend limiter must use
   the actual client address.
2. Directly connect to a loopback candidate without Caddy and send changing
   `X-Forwarded-For`, `X-Real-IP`, and `Forwarded` headers; confirm the test
   harness records the direct peer behavior and no public path can reach it.
3. Send IPv4 `198.51.100.10`, IPv4-mapped IPv6 `::ffff:198.51.100.10`, and
   compressed IPv6 variants; confirm normalization and IPv6 subnet aggregation.
4. Send six login requests with case/trim/NFKC email variants; confirm one
   canonical email bucket and generic responses.
5. Send a successful refresh followed by the same raw refresh token; confirm
   replay revocation is not bypassed by a successful request or rate-limit key.
6. Confirm `429` responses contain no email, code, token, DSN, or internal
   proxy details.

The application must bind candidate operators and database routes to a private
interface; P9.1 ops routes remain disabled by default and are not added to
Caddy. A direct local request is an operator-trust boundary, not a public
client path; if that distinction cannot be guaranteed, keep `trust proxy=false`
and accept the shared public bucket until the edge is corrected.

## Evidence required before activation

- active Caddyfile hash and validated proxy header behavior;
- Express setting and rate-limit configuration from the candidate image;
- positive real-client-IP test through Caddy;
- negative spoofed-header test from the public side;
- IPv4/IPv6 normalization result;
- restart reset observation and operator alert policy;
- one-instance topology proof and no Redis/Qdrant/Mem0/queue service.
