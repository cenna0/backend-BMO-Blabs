# P9.1 Trusted Proxy and Rate Limiting

**Decision status:** `TECHNICAL_DECISION_AUTHORIZED — LOCKED FOR FIRST CANARY`

## Observed topology

```text
Public client → Caddy TLS edge → loopback Backend :3000
                                  ├─ loopback Audio :8001
                                  └─ loopback Hermes :8642
```

The current production Backend uses host networking and listens on
`127.0.0.1:3000`. The active Caddy configuration is now inspected and
authoritative: `api.personalbmo.web.id` terminates HTTPS and reverse-proxies
directly to `127.0.0.1:3000` through exactly one intended hop. Caddy does not
perform custom forwarded-header manipulation. Caddy intercepts `/livez` and
`/readyz` and returns public 404 responses. The Backend has no public listener.

## Verdict

The readiness branch now installs an explicit Express trust function in both
the normal Backend runtime and the isolated P9 candidate. It trusts only
`127.0.0.1`, `::1`, and `::ffff:127.0.0.1`. It never uses
`trust proxy = true` or a generic hop count.

The locked configuration is:

```ts
app.set("trust proxy", (ip: string) =>
  ip === "127.0.0.1" ||
  ip === "::1" ||
  ip === "::ffff:127.0.0.1"
);
```

This trusts only the verified loopback hop, not `true`, a hop count, a public
CIDR, or arbitrary client headers. Application code does not read
`X-Forwarded-For`, `X-Real-IP`, or `Forwarded` to derive identity. Express
derives `req.ip` after applying the trust function, and the rate-limit helpers
normalize that value with the pinned `express-rate-limit` IPv6 key generator.
IPv4-mapped IPv6 client addresses resolve to their IPv4 identity; IPv6 clients
use the documented `/56` limiter aggregation.

Caddy remains unchanged by this task. Its inspected one-hop behavior is
compatible with the locked application policy. See [Caddy reverse_proxy forwarded-header behavior](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)
and [Express proxy guidance](https://expressjs.com/en/guide/behind-proxies.html).

## Limiter policy

| Route class | Limit | Key | Response |
|---|---:|---|---|
| Registration | 5 / 15 min | canonical client IP + normalized email | `429 {"error":"RATE_LIMITED"}` |
| Login | 5 / 15 min | canonical client IP + normalized email | generic `429`; no account existence |
| Refresh | 20 / 15 min | normalized `req.ip` | generic `429`; rotation/replay still executes server-side |
| Pairing issue/claim | 10 / 15 min | normalized `req.ip` plus authenticated user where available | generic `429`; no code/pairing enumeration |

Use `express-rate-limit@8.6.1` with the explicit normalized `req.ip` helper
and `/56` IPv6 aggregation. Normalize IPv4-mapped IPv6 values to the same
canonical IPv4 representation before any composite key. The limiter must not
use `X-Forwarded-For`, `X-Real-IP`, `Forwarded`, email, device ID, pairing ID,
or Authorization text as a standalone trust signal.

The limiter is intentionally single-instance in-memory. It resets on Backend
restart and does not coordinate parallel instances. No Redis is added. During
the future canary only one Backend instance may receive the candidate traffic;
the reset limitation must be monitored and documented.

## Header and direct-access tests

The readiness branch regression suite passes these cases in
`backend/tests/trusted-proxy.test.ts`; no spoofed test is sent to production:

1. A trusted loopback request resolves the intended forwarded client address.
2. Spoofed `X-Forwarded-For`, `X-Real-IP`, and `Forwarded` from an untrusted
   remote address are ignored.
3. IPv4, IPv6, and IPv4-mapped loopback/client values are handled.
4. Mapped and plain IPv4 values use the same rate-limit key.
5. The existing ops-route tests prove database diagnostics are disabled by
   default and only available when the isolated candidate explicitly opts in.
6. Existing auth/refresh/pairing tests retain generic responses and replay
   protection; no secret-bearing limiter response is added.

The application must bind candidate operators and database routes to a private
interface; P9.1 ops routes remain disabled by default and are not added to
Caddy. A direct local request is an operator-trust boundary, not a public
client path. The first canary must verify the inspected Caddy topology remains
one loopback hop.

## Evidence required before activation

- active Caddyfile hash and inspected one-hop topology;
- Express trust function and rate-limit configuration from the candidate image;
- positive real-client-IP test through a trusted loopback proxy;
- negative spoofed-header test from an untrusted remote address;
- IPv4/IPv6 normalization result;
- restart reset observation and operator alert policy;
- one-instance topology proof and no Redis/Qdrant/Mem0/queue service.
