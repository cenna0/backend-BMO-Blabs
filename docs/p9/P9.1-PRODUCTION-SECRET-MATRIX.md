**Status:** `LOCKED_FOR_FIRST_CANARY` design; no real value is provisioned.
This matrix is self-contained and must be reconciled with actual image UID/GID
and read-only mounts during a future canary. The placeholders
`<verified-group>` and `<verified-uid:gid>` are not final permissions.

Host baseline: `/opt/bmo/secrets/p9.1/`, root-owned parent, directories no
broader than `0750`, individual files `0400` or `0440` only after effective
consumer access is verified. Container mounts are read-only under
`/run/secrets/`. No symlinks, hard links, world access, or repository paths.

## Service “must never access” rules

- **Backend:** never receives owner, migration, backup, restore, backup
  encryption, SSH/Tailscale, or raw invitation material.
- **PostgreSQL:** never receives JWT, pairing HMAC, backup encryption, SSH, or
  raw invitation material. Owner material is bootstrap/break-glass only.
- **Migration:** never receives JWT, pairing HMAC, backup key, or owner value
  after bootstrap.
- **Backup:** never receives JWT, pairing HMAC, owner, migration, restore, or
  operator SSH material.
- **Restore:** never receives JWT, pairing HMAC, Backend app, owner, migration,
  or operator SSH private material unless a separately approved restore step
  requires a break-glass boundary.
- **Audio, Hermes, and Caddy:** receive none of the P9.1 secrets.
- **Mobile clients:** receive no server secret, database credential, backup key,
  or raw invitation storage permission.
- **Operator PC:** receives only encrypted backup artifacts, checksum,
  sanitized manifest, and encrypted recovery archives.

## Evidence required for each row

The future acceptance record must show secret identifier/version, intended
consumer, host owner/group/mode, effective container UID/GID, read-only mount,
startup validation, least-privilege result, rotation result, and recovery-copy
verification. It must not include values, prefixes, fingerprints, environment
dumps, or database contents.
