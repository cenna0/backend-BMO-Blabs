## Schema and migration verdict

The minimum P9.1 schema contains exactly eleven models: `User`,
`PasswordCredential`, `AuthIdentity`, `Invitation`, `Session`, `RefreshToken`,
`Device`, `DevicePairing`, `UserSettings`, `DeviceSettings`, and `AuditEvent`.
No speculative P9.2–P9.6 tables were added.

The original migration is `20260804110000_p9_1_foundation`. The review fix is
the forward-only migration `20260804123000_p9_1_integrity_constraints`, which
adds:

- unique Session family and `(id, familyId)` keys;
- composite RefreshToken-to-Session family FK;
- composite DevicePairing-to-Device owner FK;
- composite Session client-device owner FK;
- lower/trim checks for User and Invitation emails;
- Argon2id credential-format check;
- pairing attempt bounds;
- Asia/Jakarta timezone check;
- Prudence, playback-volume, and speech-speed checks.

`prisma migrate deploy` applied both migrations to an empty `bmo` database
and a fresh `bmo_zero2` database. A repeat deploy reported no pending
migrations. Normalized schema-only dumps matched; the only raw dump difference
was PostgreSQL's per-dump `restrict` token. The migration does not run at
container startup and no `db push`, reset, or blind down migration was used.

Direct SQL probes that accepted mismatched refresh families, cross-owner
pairings, padded/cased email, and UTC settings against the pre-fix schema now
fail with the named constraints. Probe rows remaining in the candidate DB:
zero. Audit rows have no public update/delete route; application audit writes
are append-only.

Default-device consistency is a service transaction invariant protected by
`pg_advisory_xact_lock(hashtextextended(userId, 0))`. Concurrent settings
updates and unpair transitions use the same per-user lock; unpair now clears a
revoked default row before promoting a replacement.

**Verdict:** migration-safe for isolated P9.1 introduction and review-approved
for later merge planning. Production rollout still requires the documented
expand/contract and pre-deploy backup procedure.

## Authentication, JWT, and session verdicts

Password hashing uses `argon2@0.45.1` Argon2id with memory cost `19,456 KiB`,
time cost `3`, parallelism `1`, 32-byte output, and unique 16-byte salts. No
plaintext password or hash is logged or returned. A bounded four-concurrent,
12-hash workload measured 422.81 ms median, 703.60 ms p95, 909.07 ms maximum,
83.66 ms maximum event-loop delay, and 85.5 MiB cgroup peak.

Login normalizes email with NFKC/lower/trim, uses generic authentication
errors, performs a dummy Argon2 verification for unknown/invalid users, and
audits success/failure without credentials. There is no disabled/deleted
account field in the locked P9.1 model; that lifecycle is not claimed here.

Access tokens use `jose@6.2.8`, explicit HS256, issuer `bmo-p9`, audience
`bmo-mobile`, and a 900-second lifetime. Claims are limited to `sub`, `sid`,
`iss`, `aud`, `iat`, and `exp`; verification allow-lists HS256 and validates
identity, session, issuer/audience, expiry, issued-at type/range, and temporal
ordering. Runtime startup rejects missing or under-32-byte JWT and pairing
secrets. Secrets are external to Git and image layers.

The current implementation has a single external JWT secret and no overlapping
`kid` rotation. Required production key rotation is therefore a controlled
maintenance action: take a verified backup, disable the P9 flag/routes, revoke
all active sessions or force reauthentication, replace the external secret,
restart the application, and verify old tokens fail before re-enabling. A
dual-key zero-downtime rotation procedure is not implemented.

Refresh values are 32-byte opaque random tokens; only SHA-256 hashes are
stored. Rotation conditionally marks the old row used and creates one
successor in one transaction. A concurrent loser or replay commits complete
family revocation and audit before returning the generic 401. Four bounded
HTTP integration executions exercised the concurrent refresh race; each
observed one 200 and one 401, and replay of both old and rotated values was
rejected. Current-session and all-session logout revoke access through the
session check as designed.

**Verdict:** authentication, JWT validation, rotation, replay, and revocation
are review-approved. Production key ownership/rotation remains a production
gate.

## Invitations, pairing, ownership, and settings

Invitation creation is operator-only, generates a 32-byte opaque secret, and
stores only its SHA-256 hash. The raw token is displayed once by the operator
workflow and is never logged or persisted by the application. Registration
consumes the invitation atomically with user, credential, identity, settings,
session, and audit creation. Concurrent registration produced `[201, 400]`;
invalid, reused, and expired invitations returned generic 400 responses. The
final expired fixture persisted `EXPIRED` plus `INVITATION_EXPIRED` audit state.
Email delivery and password-reset email are not implemented.

Pairing issuance is authenticated-user scoped in P9.1, with six numeric digits,
10-minute TTL, HMAC-SHA-256 keyed by an external pepper, one active code per
user, bounded five attempts, expiry, revoke, replay protection, and rate
limits. The claim transaction locks the user, uses a timing-safe digest
comparison, and atomically creates one owned device. Four bounded integration
executions observed one successful concurrent claim and one 409; replay,
wrong-owner, and five-wrong-code cases were rejected. No raw code appears in
database rows, audit metadata, logs, or responses beyond the one-time issue
response. Final hardware-channel identity binding is a later HW/mobile
integration gate; the P9.1 backend contract requires authenticated ownership.

Every device read/update/unpair and settings operation filters by authenticated
owner. Cross-user device, settings, and pairing requests returned 404 without
identifier enumeration. Unpair revokes the device, its client sessions and
refresh tokens, outstanding issued pairings, and repairs the default-device
flag under the user transaction lock.

User settings persist language, response length, automatic-memory-candidate
preference, and fixed `Asia/Jakarta`. Device settings persist display name,
default flag, volume, quiet hours, notification behavior, Prudence profile, and
speech speed. Validation and database checks enforce the locked ranges and
wraparound quiet hours. Persisted voice settings resolve only to Piper
`en_GB-semaine-medium`, speaker Prudence, ID 0; P9.1 does not change Audio
Service behavior, model downloads, fallback, RVC, or existing voice endpoints.

## Rate limiting and operational routes

`express-rate-limit@8.6.1` limits registration/login to five per 15 minutes
per IPv6-safe IP plus canonical email, refresh to 20 per window per IP, and
pairing to ten per window per IP. Express's default `trust proxy=false` is
consistent with the isolated direct-container topology and ignores
attacker-controlled forwarded headers. A later Caddy deployment must keep that
decision explicit; the current limiter is in-memory, single-instance, and
resets on restart. No Redis was added.

Normal `createP9Runtime` does not mount `/api/v1/ops/db/*`. Only the isolated
candidate server opts in, and it has an internal-only Docker network with no
published port. Liveness, readiness, and migration status responses are
sanitized; no DSN, credential, SQL, table contents, or mutation endpoint is
exposed. Database stop/recovery probes returned readiness `503` then `200`
without a Backend restart.

## Backup and restore verdict

The operator backup uses `pg_dump --format=custom --no-owner --no-privileges`,
streams directly into GnuPG symmetric AES-256 encryption using an external
passphrase file, writes atomically, sets mode 600, and writes a SHA-256
checksum of the encrypted artifact. Retention classification is deterministic
by `p9-daily-`/`p9-weekly-` timestamp names and retains seven daily/four weekly
artifacts. The latest final review artifact was:

- file: `p9-daily-20260804T120051Z.dump.gpg`;
- SHA-256: `bf539bde51763500862a4cb018f4b46dc1c63a36d4fd72ab9c93c2c736326448`;
- checksum verification: passed;
- mode: 600;
- GPG packet: AES-256, salted/iterated SHA-512;
- partial temporary files in its output directory: zero.

Corrupted ciphertext failed checksum validation before target creation; a
wrong passphrase failed GPG decryption. The final artifact restored into fresh
isolated database `bmo_review_restore3_20260804`. Row counts were 50 users, 50
password credentials, 72 invitations, 76 sessions, 12 devices, 31 pairings,
50 user settings, 12 device settings, and 544 audit events. Orphan-device and
orphan-pairing checks were zero; all restored password rows retained
`$argon2id$` prefixes and all restored timezones/voices remained locked.

A disposable application instance against that restored database successfully
performed login (`200`) and `/api/v1/me` (`200`), with no password/hash/pairing
credential fields exposed. The off-VPS destination/provider, production key
ownership, key rotation, scheduling, and monitoring remain OPEN. Disaster
recovery is not complete until an off-VPS destination and separate key boundary
are approved.
