# P9.1 Production Migration Plan

Status: proposed; not executed. This document is a future operator runbook,
not authorization to install PostgreSQL or run a migration.

## Migration identity and SQL review

The first application migration is `20260804110000_p9_1_foundation`. The
follow-up integrity migration is `20260804123000_p9_1_integrity_constraints`.
Both are committed under `backend/prisma/migrations/` and must be applied with
`prisma migrate deploy`; `prisma db push`, reset, and HTTP migration endpoints
are prohibited.

The foundation migration creates the P9.1 enums and tables for users,
identities, invitations, sessions, devices, pairings, user settings, device
settings, and audit events. Identifiers are UUIDs, event fields use
`timestamp(3) with time zone`, and the declared timezone default is
`Asia/Jakarta`. Foreign keys and indexes are generated by Prisma. The SQL does
not install an extension and does not create P9.2–P9.6 runtime tables.

The integrity migration adds the constraints Prisma cannot express fully:

- lower/trimmed email checks and the normalized-email uniqueness index;
- Argon2id password-hash shape checks;
- pairing-code attempt and expiry bounds;
- `Asia/Jakarta` checks on timezone columns;
- voice, volume, and speech-speed bounds;
- composite session-family and device-owner foreign keys;
- uniqueness needed to prevent ambiguous refresh families and active ownership.

The migrations are transactional at the PostgreSQL statement level unless
PostgreSQL reports a lock or constraint failure. A failed `migrate deploy`
must leave the migration unrecorded or visibly failed in `_prisma_migrations`;
the operator must not edit that table manually. Capture the error, preserve
the database for inspection, and use a corrective forward migration or a
verified restore.

## Preconditions and verification

Before any future execution:

1. Confirm the exact final main SHA and image source label.
2. Confirm an empty, private PostgreSQL database and a tested backup path.
3. Provision separate owner, migration, application, and backup credentials.
4. Inspect both migration SQL files and their checksums from the exact image.
5. Confirm PostgreSQL health, disk headroom, connection headroom, and stop
   thresholds from the readiness resource budget.

After deployment, verify `_prisma_migrations` contains both exact migration
names with successful completion, the expected table/constraint/index count,
and no unexpected extension or schema object. Run representative application
queries and the acceptance matrix before enabling any public P9.1 route.

The empty-database rehearsal and second fresh-database comparison are already
part of the independent P9.1 evidence. Production execution remains a new
gate because no production database currently exists.

## Bootstrap sequence

The future sequence is:

1. Provision secrets without putting them in shell history, Git, image layers,
   or evidence.
2. Create the private data directory with the approved UID/GID and mode.
3. Start the pinned PostgreSQL image on a dedicated private Docker network.
4. Verify health, digest, cgroup, PID, disk, and no-public-port conditions.
5. Create roles and database using the administrative credential.
6. Run `prisma migrate deploy` once from the approved application image.
7. Verify migration state, schema objects, and application queries.
8. Create the first operator invitation through the operator-only command;
   display the raw invitation once and record only its audit identity.
9. Start a private Backend candidate with P9.1 routes disabled by default.
10. Create and verify a local encrypted backup, upload only after an approved
    off-VPS destination exists, and complete an isolated restore checkpoint.

No step is executed by this readiness branch.

## Rollback policy

Application rollback is preferred after a successful schema migration. Do not
run a blind down migration. Keep the database and migration history intact,
restore the prior Backend image/configuration, and use a corrective forward
migration if the old application cannot read the schema. A destructive restore
is allowed only into a fresh isolated target unless an incident procedure has
been explicitly approved.

## Observability

Capture migration start/end, duration, exit status, migration names, lock
waits, database restart count, and post-migration query results. Do not record
DSNs, credentials, SQL containing secret values, invitation material, tokens,
or database contents in logs.
