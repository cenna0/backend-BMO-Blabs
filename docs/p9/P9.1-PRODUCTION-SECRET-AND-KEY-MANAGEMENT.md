# P9.1 Production Secret and Key Management

**Status:** `LOCKED_FOR_FIRST_CANARY` design; not provisioned, not active, and
not deployed.

No real production secret exists in this readiness branch. This document is
the canonical technical reference for another trusted engineer or operator. It
describes the future production boundary without creating files, changing
Compose, starting PostgreSQL, or running a migration.

## 1. Plain-language rules

A secret is a value that grants access or proves identity. A key is a secret
used to sign, authenticate, encrypt, or verify data. A database role is a named
PostgreSQL identity with a specific set of permissions. A read-only secret
mount lets a container read a host-provided file without allowing the
container to rewrite that file.

The operator is the ultimate owner of every P9.1 production secret. Root access
on the VPS is the provisioning authority. Each service receives only the
secrets needed for its job. Convenience is never a reason to share a
credential.

The states used in this package are:

- **Planned:** described here, but no file or value exists.
- **Provisioned:** the operator created and permission-checked the value.
- **Active:** a running approved service is consuming it.
- **Verified:** a non-secret evidence record proves the intended consumer,
  permission boundary, startup behavior, and recovery procedure.

This branch is **planned only**. No real production secret has been generated,
provisioned, mounted, or activated.

## 2. Approved injection boundary

Production secrets are file-injected. The planned host root is:

```text
/opt/bmo/secrets/p9.1/
```

It must be created by root, remain outside Git and the repository, never be in
the Docker build context, and never be copied into an image or backup
artifact. The consuming service receives a read-only mount at:

```text
/run/secrets/<secret-name>
```

The production Compose/project configuration must mount each file only into
its intended service. The current isolated candidate still interpolates JWT
and pairing values as environment variables; that is accepted for isolated
testing only and is not the production injection model. This task does not
change the candidate Compose or application source.

Compose file-based secret behavior must be inspected at provisioning time. A
bind mount does not automatically remap host ownership or permissions. The
operator must verify the actual container UID/GID and effective read access
before choosing the final file mode. Do not assume a Compose `uid`, `gid`, or
`mode` field is enforced unless the running container proves it.

Prohibited practices include secrets in Git, Compose literals, Dockerfiles,
build arguments, image layers, command arguments, shell history, startup
output, health or readiness responses, audit metadata, public diagnostics,
world-readable files, symlink-based secret paths, and one shared credential for
all PostgreSQL roles. Do not recursively change ownership of the whole BMO
tree. Do not use a world-writable permission mode.

## 3. Logical directory and permission model

This is the intended logical tree. It is a design, not a command to execute in
readiness work:

```text
/opt/bmo/secrets/p9.1/                 root:<verified-admin-group> 0750 max
├── backend/                           root:<verified-backend-group> 0750 max
│   ├── jwt-signing-key-v1              root:<verified-backend-group> 0440 max
│   └── pairing-hmac-key-v1             root:<verified-backend-group> 0440 max
├── postgres/                           root:<verified-db-group> 0750 max
│   ├── postgres-owner-password         root:<verified-db-group> 0440 max
│   ├── postgres-migration-password     root:<verified-migration-group> 0440 max
│   ├── postgres-app-password           root:<verified-backend-group> 0440 max
│   ├── postgres-backup-password        root:<verified-backup-group> 0440 max
│   └── postgres-restore-password       root:<verified-restore-group> 0440 max
└── backup/                             root:<verified-backup-group> 0750 max
    └── backup-encryption-material-v1   root:<verified-backup-group> 0440 max
```

The placeholders in angle brackets are deliberately not final numeric IDs.
The provisioning checklist must record the actual UID/GID and mode after
checking the approved image and process. A root-only consumer may instead use
an individual file mode of `0400`. A non-root consumer may use `0440` only
when the verified service group is the only intended reader. No file may have
world access.

### Isolated restored-target acceptance password

The operator-managed canonical acceptance input is
`/opt/bmo/secrets/p9.1/acceptance/login-password-v1`, supplied through
`P9_ACCEPTANCE_PASSWORD_FILE`. It remains a regular non-symlink file owned by
`bmo-admin:bmo-admin` with mode `0600`. The host launcher validates this file
before starting any Docker lifecycle operation.

The disposable fixture worker does not consume that host file as its
`1000:1000` runtime file. For `fixture-create`, the launcher mounts the
canonical file read-only only as `/run/secrets/acceptance_password_source` and
adds a container-local tmpfs at `/run/bmo-p9.1`. The root bootstrap entrypoint
copies the source into `/run/bmo-p9.1/acceptance-password`, sets owner/group
`1000:1000` and mode `0600`, then drops privileges before executing the real
worker. The worker validates and reads only that ephemeral path. The tmpfs is
removed with the disposable worker, and the entrypoint also unlinks the file
on normal child exit or failure cleanup. No persistent host duplicate,
plaintext environment value, CLI secret, or repository secret is created.

### Isolated acceptance fixture state

The acceptance fixture state is not a credential, but it is protected because
it authorizes exact cleanup of synthetic rows. The host canonical
`P9_ACCEPTANCE_STATE_FILE` remains operator-owned `bmo-admin:bmo-admin` mode
`0600` and is atomically updated. It contains only the restore database, run
identity, synthetic identity markers, display name, and user ID. Pre-fixture
aggregate evidence does not require this file. Stateful workers receive a
read-only source mount at `/run/secrets/acceptance_state_source`; the root
bootstrap entrypoint copies it to the separate container-local tmpfs file
`/run/p9-acceptance/fixture-state.json`, owned by `1000:1000` mode `0600`, then
drops privileges. The runtime file is removed on worker exit or failure, and
the host file remains until exact fixture cleanup succeeds. State contents are
never passed through environment variables or command arguments and are never
printed in operator output.

There is one canonical `postgres-app-password` file in the PostgreSQL part of
the tree. It is mounted read-only into Backend; a duplicate file is not
necessary. Do not create symlinks or hard links to make a credential appear in
multiple directories. A separate read-only mount of the same canonical file is
allowed only when the access matrix explicitly permits it.

Safe metadata checks print only paths, owners, groups, modes, and byte counts:

```sh
set -eu
secret_root=/opt/bmo/secrets/p9.1
test -d "$secret_root"
find "$secret_root" -xdev -type l -print -quit | (! grep -q .)
find "$secret_root" -maxdepth 3 -type f -printf '%M %u:%g %s %p\n'
```

The command above is a future validation command. It must not be run against
this readiness worktree as a substitute for provisioning.

## 4. Secret inventory

### Backend authentication

#### JWT signing key v1

Purpose: sign and verify short-lived HS256 access tokens. It is independent of
all database and backup credentials, has at least 32 bytes of cryptographic
entropy, and is preferably 64 random bytes represented as non-secret file
content. Backend is its only consumer.

PostgreSQL, the migration process, Audio, Hermes, Caddy, backup, restore, and
the operator PC must never receive it. The Backend must fail before binding P9
routes when the file is missing, empty, weak, unreadable, or outside the
approved versioned path. Health and audit output report only a sanitized
failure class.

#### Pairing HMAC key v1

Purpose: produce the keyed SHA-256 digest for six-digit pairing codes. It is a
separate random value with at least 32 bytes of entropy. Only the Backend
pairing subsystem consumes it.

PostgreSQL, migration, Audio, Hermes, Caddy, backup, restore, and the operator
PC must never receive it. Missing, empty, weak, or unreadable material stops
the Backend before pairing routes are enabled. Pairing remains feature-disabled
until physical-device identity binding is approved, even though the key model
is locked.

### PostgreSQL role credentials

Every role has a distinct password and a distinct purpose:

- **Owner/admin:** creates the database and roles and performs break-glass
  recovery. It is not a normal Backend, migration, backup, or restore secret.
- **Migration:** applies reviewed Prisma migrations in one controlled process.
  It is not mounted into normal Backend, Audio, Hermes, Caddy, or backup
  runtime.
- **Application:** provides normal Backend database access. It cannot create
  roles or databases, become superuser, or perform unrestricted administration.
- **Backup:** permits only the read operations required by a consistent
  `pg_dump`. It cannot mutate application data, change schema, or manage roles.
- **Restore/operator:** is used only for an isolated restore or controlled
  disaster-recovery operation. It is never normal application runtime.

The PostgreSQL server receives an owner password only during controlled initial
bootstrap if the selected image requires it. Steady-state operation must not
depend on an undocumented default password. Owner, migration, backup, and
restore values are supplied to their one-shot operator processes through
protected files, not to the normal Backend container.

The minimum privilege baseline is:

- owner/admin: database ownership and controlled role/database administration;
  break-glass only;
- migration: connect to the target database and apply the reviewed migration
  DDL in the application schema; no superuser and no normal app traffic;
- application: connect, use the application schema, and perform only the
  application table/sequence operations required by P9.1; no DDL, role, or
  database administration;
- backup: connect and read the P9.1 database consistently, including the
  metadata required by `pg_dump`; no writes, DDL, role management, or database
  creation;
- restore: connect to a named disposable target and create/restore objects
  there; never use the restore role against the production target.

The exact grants are inspected from the approved migration/image and recorded
as sanitized SQL evidence during provisioning. A grant broader than this
baseline is a stop condition.

### Backup encryption material

The first-canary model is the already validated **symmetric GPG AES-256**
model. A backup job reads versioned encryption material from the protected
backup boundary, streams `pg_dump` into GPG without retaining a plaintext dump,
and writes only the encrypted artifact, ciphertext checksum, and sanitized
manifest. The key is not stored beside the artifact or inside PostgreSQL.

The canonical first-canary material file is
`/opt/bmo/secrets/p9.1/backup/backup-encryption-material-v1`. It is created
manually outside Git during a separately approved provisioning step; it is not
present in this readiness branch or environment examples.

The operator owns the key. A recovery copy is held outside the VPS in an
encrypted operator-controlled archive, with one additional offline encrypted
copy required before final P9.1 production verification. The operator PC
receives encrypted backups and manifests; it must not receive a plaintext key
file.

The recommended future improvement is asymmetric encryption: the VPS would
hold only a public encryption key, while the operator retains the private
decryption key offline. That reduces the consequence of a VPS compromise, but
it is not the first-canary implementation and must be separately tested before
adoption.

If the symmetric key is lost and no recovery copy can decrypt it, every backup
encrypted with that key is permanently unreadable. If the VPS-held symmetric
material is suspected compromised, assume retained ciphertext can be read:
disable backup/restore operations, preserve evidence, rotate to a new key,
re-encrypt a verified recovery set where possible, and update every recovery
copy before resuming.

### Manual off-VPS transfer authentication

The approved first-canary destination is the operator-owned personal computer,
with a manual pull from the VPS. No Backblaze, Cloudflare, Google Drive,
rclone-provider, NAS, second-server, or upload credential is created. The
operator’s existing private administrative path, such as SSH or Tailscale, is
documented and verified separately from database passwords and backup
encryption material. Only the encrypted artifact, checksum, and sanitized
manifest may be transferred.

### Invitation generation

The operator-only invitation command generates a 32-byte random secret,
displays the raw value exactly once to the controlled operator channel, and
persists only its secure hash. There is no permanent invitation master secret
in P9.1. The raw invitation is never written to a file, log, ticket, audit
metadata, backup, or evidence. If it is exposed, revoke that invitation and
create a replacement.

### Internal operations routes

No broadly shared operations bearer credential exists in P9.1. Database
liveness/readiness/migration routes are disabled by default, private, sanitized,
and never perform migration or mutation over HTTP. If a future operator
boundary requires a credential, it must be a separately owned file-injected
value and must not be accepted by public routes. No operator credential is
sent to Audio, Hermes, Caddy, PostgreSQL, or mobile clients merely to simplify
access.

## 5. Service isolation rules

| Service/process | May read | Must never read or receive |
|---|---|---|
| Backend | JWT v1, pairing HMAC v1, PostgreSQL application password | owner, migration, backup, restore passwords; backup encryption/recovery material; invitation raw values; operator SSH/Tailscale credentials |
| PostgreSQL bootstrap/server | owner password only for controlled initialization as required by the image | JWT, pairing HMAC, backup encryption/recovery material; migration/app/backup/restore values unless the approved operation explicitly needs them |
| Migration process | migration password and database endpoint | JWT, pairing HMAC, owner password after bootstrap, backup key, operator credentials |
| Backup process | backup-role password and first-canary GPG encryption material | JWT, pairing HMAC, owner/migration passwords, restore password, operator credentials |
| Restore process | restore-role password and approved recovery key material | JWT, pairing HMAC, Backend app password, operator SSH/Tailscale private key |
| Audio Service | none of the P9.1 secrets | every P9.1 auth, database, pairing, invitation, and backup secret |
| Hermes | none of the P9.1 secrets | every P9.1 auth, database, pairing, invitation, and backup secret |
| Caddy | none of the P9.1 secrets | every P9.1 auth, database, pairing, invitation, and backup secret |
| Operator PC | encrypted backup artifact, checksum, manifest, and encrypted recovery archive | plaintext database dump, database credentials, JWT key, pairing key, raw application secrets |

The same value must not be copied into multiple service directories merely for
convenience. A service that does not appear in the “May read” column receives no
mount and no environment value.

## 6. Generation and provisioning procedures

All commands in this section are marked **FUTURE PRODUCTION ACTION — DO NOT
RUN DURING READINESS**. They are safe patterns, not executed commands. They
write values directly to protected files and never place a generated value in
terminal output or command arguments.

### Generate random material

From a root-controlled maintenance shell, first use a restrictive umask and
the final verified directory. The exact file path and group must be reviewed
against the matrix before writing:

```sh
# FUTURE PRODUCTION ACTION — DO NOT RUN DURING READINESS
set -eu
umask 077
secret_root=/opt/bmo/secrets/p9.1
install -d -m 0750 "$secret_root/backend" "$secret_root/postgres" "$secret_root/backup"
openssl rand -hex 64 > "$secret_root/backend/jwt-signing-key-v1"
openssl rand -hex 32 > "$secret_root/backend/pairing-hmac-key-v1"
openssl rand -hex 32 > "$secret_root/postgres/postgres-owner-password"
openssl rand -hex 32 > "$secret_root/postgres/postgres-migration-password"
openssl rand -hex 32 > "$secret_root/postgres/postgres-app-password"
openssl rand -hex 32 > "$secret_root/postgres/postgres-backup-password"
openssl rand -hex 32 > "$secret_root/postgres/postgres-restore-password"
openssl rand -hex 32 > "$secret_root/backup/backup-encryption-material-v1"
```

The operator must set verified owner/group/mode metadata after checking the
actual container UID/GID. Do not print, `cat`, copy, or checksum-print the
secret contents. Record only secret identifier, version, byte count, owner,
group, mode, consumer, and validation outcome.

### Safe validation

```sh
# FUTURE PRODUCTION ACTION — DO NOT RUN DURING READINESS
set -eu
secret_root=/opt/bmo/secrets/p9.1
test "$(stat -c '%a' "$secret_root")" -le 750
for path in \
  "$secret_root/backend/jwt-signing-key-v1" \
  "$secret_root/backend/pairing-hmac-key-v1" \
  "$secret_root/postgres/postgres-owner-password" \
  "$secret_root/postgres/postgres-migration-password" \
  "$secret_root/postgres/postgres-app-password" \
  "$secret_root/postgres/postgres-backup-password" \
  "$secret_root/postgres/postgres-restore-password" \
  "$secret_root/backup/backup-encryption-material-v1"; do
  test -f "$path"
  test ! -L "$path"
  test -s "$path"
  stat -c '%A %U:%G %s %n' "$path"
done
```

The expected byte counts are checked against the generation procedure without
printing the value. Backend validation additionally rejects placeholder text,
short JWT/HMAC material, missing files, unreadable mounts, and version/path
mismatch. PostgreSQL validation proves that no undocumented default password
is active. The backup job validates encryption material before starting a dump
and creates no success artifact on failure.

## 7. Startup and replacement behavior

| Condition | Backend | PostgreSQL/bootstrap | Migration/backup/restore |
|---|---|---|---|
| Missing or empty secret | Fail before P9 routes bind; sanitized error only | Refuse undocumented default; bootstrap stops | Stop before SQL/dump/restore and leave no success artifact |
| Too short or placeholder | Fail closed for JWT/HMAC/app password | Reject password setup | Stop and report only a bounded error code |
| Wrong owner/mode/unreadable mount | Fail before accepting traffic | Refuse controlled operation | Stop before consuming the database |
| Stale version or configured key mismatch | Stop; do not guess a fallback | Stop role operation | Stop and preserve prior valid artifact/copy |
| File replaced during rotation | Existing process keeps its loaded value until controlled restart; new process validates the replacement | New controlled operation validates before use | One-shot process validates before starting |
| Secret value in health/log/audit | Defect; stop and investigate | Defect; stop and investigate | Defect; quarantine evidence and stop |

No service falls back to a default, a weak development value, a command-line
value, or another service’s credential. Startup and readiness responses never
include secret values, prefixes, hashes, DSNs, passwords, tokens, or pairing
codes.

## 8. Rotation lifecycles

### JWT signing key

Current P9.1 HS256 behavior uses one active verification key and does not
implement a `kid` overlap. The safe first-canary normal rotation is therefore
a controlled cutover:

```text
v1 active → backup and private maintenance → install v2 → restart Backend
→ v2 signs/verifies → old access tokens fail immediately → refresh sessions
remain valid and issue v2 tokens → record evidence
```

1. Confirm the operator-owned recovery material and a verified database backup.
2. Disable P9.1 public flags and stop new authentication traffic.
3. Generate `jwt-signing-key-v2` in the protected secret boundary.
4. Switch the configured active key identifier and restart only the approved
   Backend candidate.
5. Verify v2 login and protected requests. Existing access tokens signed by v1
   are rejected immediately; their maximum normal lifetime would otherwise be
   900 seconds.
6. Existing opaque refresh sessions do not need normal revocation: a valid
   refresh can rotate and receive a v2 access token. Revoke all sessions for a
   suspected compromise, operator security event, or unexplained exposure.
7. Remove v1 only after evidence confirms v2 operation. If a future dual-`kid`
   implementation is introduced, an overlap may last no longer than the
   approved 900-second access-token lifetime plus a measured clock margin.

Rollback to v1 is permitted only for a non-compromise implementation failure
while v1 remains trusted. Never restore a suspected-compromised key. Record
key version and outcomes, never a key fingerprint or prefix.

### Pairing HMAC key

The simple safe rotation deliberately invalidates active pairing codes rather
than adding long-lived dual-key verification:

```text
disable issuance → revoke ISSUED codes → install v2 → restart Backend
→ wait through the 600-second code lifetime → issue new codes
```

Audit the administrative action, verify old claims fail, and verify new codes
work only after the new key is active. Claimed devices are not unpaired solely
because the HMAC key changed. Emergency compromise additionally disables
pairing, revokes device-bound sessions where applicable, investigates audit
events, and requires fresh physical-device authentication before re-enabling.

### PostgreSQL credentials

The application credential is rotated without giving Backend owner or
migration access. The preferred staged pattern is to create a temporary
least-privilege replacement application role, grant exactly the approved app
privileges, validate a fresh Backend connection using its protected file, then
switch the Backend and revoke the old role. If the reviewed deployment uses
one role name, perform `ALTER ROLE` only in a maintenance window, stage the new
file, restart Backend, validate a new pool connection, and revoke the old
credential immediately after verification. Never put either password in a
command argument.

Migration, backup, and restore credentials are one-shot credentials: stop the
corresponding job, replace the protected file, validate a fresh connection,
then resume. The owner credential rotates only through break-glass
administration after backup/recovery evidence is captured. On compromise,
revoke the affected role, recycle connections, inspect access/audit evidence,
and re-run the relevant acceptance checks. The Backend never receives owner,
migration, backup, or restore credentials.

The role-credential lifecycle is:

```text
app role v1 → create least-privilege replacement → validate fresh connection
→ switch Backend mount/config → drain pool → revoke v1

one-shot role v1 → stop its job → replace protected file → validate connection
→ run reviewed operation → revoke/retire v1

owner role → break-glass maintenance → rotate after recovery evidence
→ verify private administration → return to offline custody
```

### Backup encryption material

```text
create v2 → store encrypted recovery copy → encrypt new backups with v2
→ restore-test a v2 artifact → update PC/offline artifact set
→ retain v1 until every v1 artifact expires or is re-encrypted
```

Old backups remain readable only while their old key remains available. After
the retention window and a verified replacement set, the old key may be
retired. A lost key blocks restore of its artifacts; a suspected-compromised
key requires treating those artifacts as exposed and rotating immediately.

## 9. Recovery and escrow

Before final P9.1 production verification, the operator must maintain:

1. a primary recovery copy on the operator PC in an encrypted archive;
2. one additional offline encrypted recovery copy stored separately.

Acceptable categories include encrypted removable media, an encrypted
password-manager attachment, or an encrypted offline archive stored
separately. No provider is selected by this document. The recovery inventory
records secret version, date, purpose, storage category, and last readability
check, never the secret or a meaningful fingerprint. Do not store the recovery
key beside the encrypted backup or in plaintext on the PC.

Verify readability at initial setup, monthly, and after backup-key, backup-tool,
migration-system, or material PostgreSQL changes. A rehearsal restores the
exact PC copy into a fresh isolated database and runs schema, ownership, row,
login, and `/api/v1/me` checks. Preserve only sanitized evidence.

- If the VPS is lost, use the latest verified PC copy and recovery material to
  restore a fresh private database, then rebuild the approved application
  boundary.
- If the operator PC is lost, use the additional offline encrypted copy and
  recovery material; rotate PC access credentials after containment.
- If both are lost but the offline copy survives, follow the same recovery
  procedure and record the loss.
- If every artifact or recovery key is lost, encrypted backups are not
  recoverable. This is an accepted residual risk of the initial manual-copy
  model and must be recorded as an incident.

## 10. Evidence and prohibited handling

Successful provisioning evidence contains only:

- source SHA and image identity;
- secret identifiers and versions;
- owner/group/mode and byte-count checks;
- mount paths and consumer names;
- startup success/failure class;
- rotation/recovery test outcome;
- backup artifact name, checksum, manifest, and restore result without data or
  key material.

Never record passwords, JWTs, refresh tokens, invitation secrets, pairing
codes, GPG material, private keys, DSNs, database rows, or process-environment
dumps. Never put a secret in a ticket, shell command argument, copied command
line, image layer, Git diff, or public endpoint. If a secret appears in any of
those places, stop, preserve sanitized evidence, revoke/rotate it, and follow
the incident runbook.
