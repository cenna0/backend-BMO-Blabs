# P9.1 Production Secret and Key Management

No production secret is generated, printed, committed, or provisioned by this
readiness branch. Values below are placeholders for an operator-controlled
secret boundary.

## Inventory

## Required storage boundary

The production recommendation is a root-owned secret directory such as
`/opt/bmo/secrets/p9/`, mode `0700`, with individual files mode `0600` and a
dedicated runtime reader. Docker secrets or an equivalent file-backed provider
is preferred. A secret must not be supplied in a Dockerfile, build argument,
Compose image layer, Git-tracked environment file, command argument, or backup
artifact next to the encrypted data.

The current P9 candidate reads JWT and pairing values from environment variables
and the candidate Compose file interpolates them. That is acceptable for the
isolated test only; a production canary must either use a reviewed file-backed
loader or record explicit operator acceptance of process/Docker-inspect
exposure. This readiness task does not alter that source boundary.

## Startup validation

Before P9 routes are enabled, the operator must verify without printing values:

```bash
set -eu
secret_dir=/opt/bmo/secrets/p9
test -d "$secret_dir"
test "$(stat -c '%a' "$secret_dir")" = 700
for name in postgres_app_password postgres_migration_password jwt_signing_key pairing_hmac_key backup_key; do
  path="$secret_dir/$name"
  test -f "$path"
  test "$(stat -c '%a' "$path")" = 600
  test -s "$path"
done
```

The application must reject missing, empty, weak, placeholder, or wrong-length
JWT/pairing values before binding any P9 route. Database health must fail closed
if the application role cannot connect. The operator records only file modes,
owners, validation result, and a key identifier—not secret bytes.

## JWT lifecycle

The current implementation has one HS256 key and no `kid` overlap. The safe
rotation procedure is therefore:

1. Take and verify a backup; record image, source SHA, schema version, and key
   version without recording the key.
2. Disable P9 public flags and stop new authentication traffic.
3. Revoke all active sessions in the database.
4. Replace the external key with 64 fresh random bytes and increment the key
   version in operator records.
5. Restart only the future candidate Backend; verify old access tokens fail and
   new login succeeds.
6. Confirm the public health, audit, and database readiness gates, then enable
   the approved flags.

The maximum old-token exposure window is bounded by the 900-second access-token
TTL, and the recommended rotation revokes sessions immediately. A future
dual-`kid` overlap would reduce disruption but is not implemented or selected.

## Pairing HMAC lifecycle

The HMAC key is independent of JWT. Normal rotation occurs with no active
pairing window: disable pairing issuance, revoke outstanding `ISSUED` codes,
replace the key, restart the candidate, and verify new claims. Because codes
expire after 600 seconds, dual-key verification is not required for planned
rotation. Emergency compromise response is immediate key replacement, revoke
all outstanding codes, audit the action, and inspect device ownership/session
activity.

## Backup-key lifecycle

The preferred production model keeps the GPG key offline except during a
controlled backup/restore operation. The key is not stored in the PostgreSQL
volume, same-directory metadata, Docker image, or remote object. The operator
must choose escrow custodians and recovery access. Rotating the key does not
silently rewrite old artifacts: create a verified new-key recovery set, test
restore, then retain the old key until all artifacts encrypted with it are
outside retention. Losing the key makes those backups permanently unreadable.

## Database credential lifecycle

Use separate roles: `p9_app`, `p9_migrator`, `p9_backup`, `p9_restore`, and a
break-glass owner. Rotate `p9_app` by provisioning the new password, verifying
the candidate, restarting the Backend to establish new pool connections, then
revoking the old password. Rotate migration and backup credentials after the
maintenance operation. Revoke all sessions and stop P9 traffic for emergency
credential compromise.

## Logging and evidence rules

Never log passwords, hashes, JWTs, refresh values, invitation secrets, pairing
codes, DSNs, encryption keys, Authorization headers, or raw database errors.
Log only redacted event type, actor/target opaque IDs where safe, request ID,
outcome, and bounded error code. Secret scans must inspect Git, image layers,
Compose config output, test snapshots, backup directories, and generated
evidence without printing secret contents.
