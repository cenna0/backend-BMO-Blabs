# P9.1 Production Canary Plan

Status: proposed; not executed. The plan preserves the current P8 Backend,
Audio, Hermes, Caddy, DNS, TLS, UFW, and Tailscale configuration until a
separate deployment approval exists.

## Stage A — database infrastructure canary

Run for at least 30 minutes with no public Backend replacement and no public
port. Use the pinned `postgres:16.10-alpine3.22` digest
`sha256:029660641a0cfc575b14f336ba448fb8a75fd595d42e1fa316b9fb4378742297` on
the dedicated private network. Apply migrations to a controlled empty
database, restart the candidate database once, check persistence, exercise
bounded connections, create a local encrypted backup, and restore into a new
isolated database. Stop on any resource threshold, OOM, persistence mismatch,
or production health change.

## Stage B — parallel Backend candidate

Build a fresh image from the approved final main SHA after readiness decisions
are merged. Bind the candidate only to a separate loopback port and private
network; do not add a Caddy route. Keep P9.1 flags disabled until database and
secret checks pass. Run at least 60 minutes and complete:

- 20 health/readiness checks;
- 10 invite/registration cases;
- 20 login success/failure and rate-limit cases;
- 20 refresh rotation/replay/logout cases;
- 10 ownership and settings cases;
- 10 pairing issue/claim/replay/race cases when hardware binding is available;
- 12 legacy voice and WebSocket regression cases against unchanged Audio and
  Hermes endpoints.

The candidate must use only the candidate database and must not access the
production database or production networks.

## Stage C — controlled replacement canary

Only after A and B pass, preserve the current Backend image digest and config,
take a fresh backup, and obtain explicit deployment approval. Replace only the
Backend behind the existing loopback/Caddy path; keep Audio and Hermes
unchanged. Start with a 15-minute controlled observation window, then soak for
at least 120 minutes. Verify 50 public health checks, 12 legacy voice/WebSocket
cases, and the approved P9.1 cases with feature flags staged independently.

Immediate rollback triggers are public health failure, legacy voice regression,
memory or kernel-OOM threshold breach, restart increase, database error spike,
auth/replay defect, or any secret exposure.

## Stage D — final verification

After the soak, verify backup age/checksum/encryption, migration state,
restart persistence, authentication lifecycle, ownership isolation, pairing
only where hardware binding is proven, private ops endpoints, and rollback
readiness. Record all evidence before declaring the canary complete.

## Feature flags

The future deployment should expose independent, default-safe controls:

| Flag | Default | Canary use |
|---|---|---|
| `P9_ENABLED` | false | master gate |
| `P9_AUTH_ENABLED` | false | enable after private auth tests |
| `P9_INVITE_REGISTRATION_ENABLED` | false | operator-approved invite window |
| `P9_PAIRING_ENABLED` | false | remains off until hardware binding passes |
| `P9_SETTINGS_ENABLED` | false | enable after ownership tests |
| `P9_OPS_ENABLED` | false | private operator context only |

Disabled routes must return a deliberate sanitized disabled response or 404,
according to the final route contract. No flag may bypass authentication,
ownership, or rate limits. No migration is available over HTTP. Existing voice
and WebSocket routes remain independently controlled.

## Go/no-go evidence

Each stage requires clean Git state, exact image/source labels, secret scans,
hardware-contract hash verification, production health comparison, resource
measurements, and an operator sign-off. This branch provides the plan only.
