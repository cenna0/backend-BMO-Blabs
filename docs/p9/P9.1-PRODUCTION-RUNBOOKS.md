# P9.1 Production Readiness Runbooks

These commands are templates for a separately approved canary. They are not
to be executed from this branch. Every command assumes a private maintenance
shell, explicit operator approval, and a preflight check. Secrets are supplied
through files or an approved secret manager; they are never placed in command
arguments, shell history, logs, Git, or evidence.

## Common preflight

```sh
set -eu
umask 077
test "$(git -C /opt/bmo/app branch --show-current)" = main
test -z "$(git -C /opt/bmo/app status --porcelain)"
git -C /opt/bmo/app rev-parse HEAD
docker info >/dev/null
test "$(curl -fsS -o /dev/null -w '%{http_code}' https://bmo.example/health)" = 200
```

Replace the example public host with the approved existing host only during a
future deployment. Do not run this readiness branch against production.

**FUTURE PRODUCTION ACTION — DO NOT RUN DURING READINESS.** Create the root
owned directory outside Git, check the actual service UID/GID, generate values
directly into protected files, and mount only the intended files read-only at
`/run/secrets/<secret-name>`. Do not assume Compose remaps ownership. Validate
only path, owner, group, mode, byte count, mount target, and pass/fail outcome:

```sh
set -eu

test -d "$secret_root"
find "$secret_root" -xdev -type l -print -quit | (! grep -q .)
find "$secret_root" -maxdepth 3 -type f -printf '%M %u:%g %s %p\n'
```

Final numeric modes remain a provisioning-time check. Do not generate
production keys or passwords in this readiness branch.

## Initialize private PostgreSQL

```sh
cd /opt/bmo/app
test -f p9.1-compose.yml
test ! -e /opt/bmo/p9.1-data/postgres/PG_VERSION
install -d -m 0700 -o bmo-admin -g bmo-admin /opt/bmo/p9.1-data/postgres
P9_DATA_DIR=/opt/bmo/p9.1-data/postgres \
P9_POSTGRES_PASSWORD_FILE=/opt/bmo/secrets/p9.1/postgres/postgres-owner-password \
docker compose -f p9.1-compose.yml -p bmo-p9-1 config >/dev/null
P9_DATA_DIR=/opt/bmo/p9.1-data/postgres \
P9_POSTGRES_PASSWORD_FILE=/opt/bmo/secrets/p9.1/postgres/postgres-owner-password \
docker compose -f p9.1-compose.yml -p bmo-p9-1 up -d postgres
docker compose -f p9.1-compose.yml -p bmo-p9-1 ps postgres
```

Verify the pinned digest, private network, `127.0.0.1`-free published-port
list, health, memory/PID/CPU limits, and data-directory ownership before any
application connection. The production version of this command must use a
reviewed production compose file; the committed candidate compose is not a
production deployment artifact.

## Roles, database, and migration

Create owner, migration, application, and backup roles using an interactive
protected administrative session. Never use a password on a command line.
Grant only the privileges recorded in the secret/key document. Then inspect
the exact SQL and apply migrations from the approved image:

```sh
cd /opt/bmo/app/backend
npm ci --ignore-scripts
npm run prisma:generate
npm run prisma:validate
npm run prisma:migrate:deploy
```

Verify `_prisma_migrations`, table/constraint/index inventory, and an
application query. Do not run `db push`, reset, or a down migration.

## First invitation and bootstrap

With the database private and P9 routes disabled publicly:

```sh
cd /opt/bmo/app/backend
npm run p9:invite -- --email operator@example.invalid --expires-in-hours 72
```

Capture the one-time token directly to the operator’s secure channel; do not
copy it into logs, tickets, evidence, or shell history. Verify only the audit
event, expiry, and hash-only database representation. The example address is a
placeholder and must be replaced only by the approved operator.

## Backup, manual PC pull, and restore

Current rehearsal state: `SSH V3 VERIFIED / ENCRYPTION MATERIAL PROVISIONED AND PREFLIGHT VALIDATED /
BACKUP ARTIFACT NOT YET CREATED / WINDOWS TRANSFER NOT YET EXECUTED`. The canonical encryption-material file is
`/opt/bmo/secrets/p9.1/backup/backup-encryption-material-v1`. The approved Windows root is
`D:\codex\BMO-backups`; the active incoming destination is
`D:\codex\BMO-backups\incoming`. The off-VPS action is a Windows-side
`scp.exe` pull over Tailscale, never a VPS push.

The committed local foundation is invoked from the Backend directory:

```sh
cd /opt/bmo/app/backend
P9_BACKUP_PASSPHRASE_FILE=/opt/bmo/secrets/p9.1/backup/backup-encryption-material-v1 \
npm run p9:backup:validate-config
```

This is a configuration-only preflight. It loads the same backup validation
boundary, validates the protected material, and stops before creating the
output directory or invoking Docker, PostgreSQL tooling, `pg_dump`, or GPG. It
creates no backup artifact. A successful preflight is required before the real
backup rehearsal.

The real backup command is then invoked only with the separately approved
output directory and observed migration state:

```sh
cd /opt/bmo/app/backend
P9_BACKUP_DIR=/opt/bmo/p9.1-backups/daily \
P9_BACKUP_PASSPHRASE_FILE=/opt/bmo/secrets/p9.1/backup/backup-encryption-material-v1 \
P9_POSTGRES_MAJOR_VERSION=16 \
P9_BACKUP_MIGRATION_STATE=<observed-sanitized-migration-state> \
P9_BACKUP_KIND=daily npm run p9:backup
```

Replace the migration-state placeholder only with an observed result from the
approved private migration check; do not use `verified` as a guess. The
current documented migration state is `not-verified` until that observed check
is performed. The
command writes the encrypted artifact, checksum, and schema-versioned
sanitized manifest only after the artifact and checksum validate.

Verify the final `.dump.gpg`, `.sha256`, and sanitized manifest, mode `0600`,
checksum, GPG decryption test, and local retention. Pull only those three files
to the Windows operator PC at least weekly and before/after the specified
migration and deployment events. Use the locked procedure in
[`P9.1-WINDOWS-OFF-VPS-BACKUP-GUIDE.md`](P9.1-WINDOWS-OFF-VPS-BACKUP-GUIDE.md):
PowerShell over verified Tailscale, Windows OpenSSH `scp.exe`, exact paths with
explicit host-key checking, PowerShell SHA-256, and interactive Gpg4win/GnuPG.
Verify checksum, plausible size, encryption readability, manifest fields, and
absence of plaintext or credentials on the PC. Retain four latest weekly
copies and three protected milestone copies. The real Windows transfer and
restore remain pending evidence; do not execute one here.
Restore from that exact PC copy into a new isolated PostgreSQL target, verify
the checksum/key, schema/migration state, row relationships, and application
queries. Never restore over production as a first test.

## Rotation, recovery, and session response

Follow the JWT, pairing HMAC, PostgreSQL-role, and backup-key procedures in the
canonical secret document. The first-canary JWT design uses one active HS256
key, so normal cutover rejects old access tokens immediately while valid opaque
refresh sessions can continue to rotate into the new key. Compromise requires
session revocation. Pairing-key rotation invalidates active ten-minute codes.
Use overlap only where a separately approved implementation supports it.

The operator PC and one additional offline encrypted copy are the approved
recovery boundary. The exact PC pull and fresh-target restore are required
before canary approval. Never transfer a plaintext dump, database credential,
JWT key, pairing key, or raw application secret.

For a controlled session revocation operation:

```sh
cd /opt/bmo/app/backend
# Run the approved operator-only session revocation procedure; no raw token is supplied.
```

No generic HTTP route may be used to rotate production keys or run migrations.

## Disable, rollback, and incident handling

Disable flags using the protected environment/configuration mechanism, restart
only the approved candidate service, and verify the sanitized health contract.
For failed migration, disk pressure, corruption, monitoring failure, or
compromise, follow the decision matrix in
[`P9.1-PRODUCTION-ROLLBACK-RUNBOOK.md`](P9.1-PRODUCTION-ROLLBACK-RUNBOOK.md)
and the individual procedures in
[`P9.1-PRODUCTION-SECRET-INCIDENT-RUNBOOKS.md`](P9.1-PRODUCTION-SECRET-INCIDENT-RUNBOOKS.md).
Stop before deleting data or rotating a key if ownership/incident scope is
unclear; escalate to the operator.
