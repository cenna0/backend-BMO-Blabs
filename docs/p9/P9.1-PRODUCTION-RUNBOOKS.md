# P9.1 Production Readiness Runbooks

These commands are templates for a separately approved canary. They are not
to be executed from this branch. Every command assumes a private maintenance
shell, explicit operator approval, and a preflight check. Secrets are supplied
through files or an approved secret manager; they are never placed in command
arguments, shell history, logs, Git, or evidence.

## Common preflight

```sh
set -eu
umask 077
test "$(git -C /opt/bmo/app branch --show-current)" = main
test -z "$(git -C /opt/bmo/app status --porcelain)"
git -C /opt/bmo/app rev-parse HEAD
docker info >/dev/null
test "$(curl -fsS -o /dev/null -w '%{http_code}' https://bmo.example/health)" = 200
```

Replace the example public host with the approved existing host only during a
future deployment. Do not run this readiness branch against production.

## Provision and validate secrets

Create the approved root-owned directory and mode, then write secrets through a
protected operator mechanism. A future implementation must use files such as
`/opt/bmo/p9.1-secrets/postgres_password`, `jwt_signing_key`,
`pairing_hmac_key`, and `backup_passphrase`, owned by the runtime account or
root as appropriate and mode `0600`. Validate without printing contents:

```sh
find /opt/bmo/p9.1-secrets -maxdepth 1 -type f -printf '%M %u:%g %p\n'
test "$(stat -c '%a' /opt/bmo/p9.1-secrets/jwt_signing_key)" = 600
test "$(wc -c < /opt/bmo/p9.1-secrets/jwt_signing_key)" -ge 32
```

The final owner, storage mechanism, and external key escrow remain operator
decisions. Do not generate production keys during this task.

## Initialize private PostgreSQL

```sh
cd /opt/bmo/app
test -f p9.1-compose.yml
test ! -e /opt/bmo/p9.1-data/postgres/PG_VERSION
install -d -m 0700 -o bmo-admin -g bmo-admin /opt/bmo/p9.1-data/postgres
P9_DATA_DIR=/opt/bmo/p9.1-data/postgres \
P9_POSTGRES_PASSWORD_FILE=/opt/bmo/p9.1-secrets/postgres_password \
docker compose -f p9.1-compose.yml -p bmo-p9-1 config >/dev/null
P9_DATA_DIR=/opt/bmo/p9.1-data/postgres \
P9_POSTGRES_PASSWORD_FILE=/opt/bmo/p9.1-secrets/postgres_password \
docker compose -f p9.1-compose.yml -p bmo-p9-1 up -d postgres
docker compose -f p9.1-compose.yml -p bmo-p9-1 ps postgres
```

Verify the pinned digest, private network, `127.0.0.1`-free published-port
list, health, memory/PID/CPU limits, and data-directory ownership before any
application connection. The production version of this command must use a
reviewed production compose file; the committed candidate compose is not a
production deployment artifact.

## Roles, database, and migration

Create owner, migration, application, and backup roles using an interactive
protected administrative session. Never use a password on a command line.
Grant only the privileges recorded in the secret/key document. Then inspect
the exact SQL and apply migrations from the approved image:

```sh
cd /opt/bmo/app/backend
npm ci --ignore-scripts
npm run prisma:generate
npm run prisma:validate
npm run prisma:migrate:deploy
```

Verify `_prisma_migrations`, table/constraint/index inventory, and an
application query. Do not run `db push`, reset, or a down migration.

## First invitation and bootstrap

With the database private and P9 routes disabled publicly:

```sh
cd /opt/bmo/app/backend
npm run p9:invite -- --email operator@example.invalid --expires-in-hours 72
```

Capture the one-time token directly to the operator’s secure channel; do not
copy it into logs, tickets, evidence, or shell history. Verify only the audit
event, expiry, and hash-only database representation. The example address is a
placeholder and must be replaced only by the approved operator.

## Start private parallel candidate

Build only from the approved final main SHA in a future deployment task. Use a
separate candidate project/network and loopback port; verify no Caddy route and
no production network attachment:

```sh
cd /opt/bmo/app
docker compose -f p9.1-compose.yml -p bmo-p9-1 up -d --build backend
curl -fsS http://127.0.0.1:3010/health
docker inspect bmo-p9-1-backend-1 --format '{{json .NetworkSettings.Networks}}'
```

The candidate compose above is for isolated validation. Production use
requires a separately approved image/configuration package.

## Acceptance and controlled switch

Run the commands in `P9.1-PRODUCTION-ACCEPTANCE-MATRIX.md`, save redacted
outputs, and verify production health before and after. Only after the private
parallel canary and operator sign-off may the existing Backend loopback service
be switched. Preserve its image digest/configuration and prepare the exact
rollback command before the switch. Audio and Hermes remain unchanged.

## Backup, upload, and restore

The committed local foundation is invoked from the Backend directory:

```sh
cd /opt/bmo/app/backend
P9_BACKUP_DIR=/opt/bmo/p9.1-backups/daily \
P9_BACKUP_PASSPHRASE_FILE=/opt/bmo/p9.1-secrets/backup_passphrase \
P9_BACKUP_KIND=daily npm run p9:backup
```

Verify the final `.dump.gpg` and `.sha256` files, mode `0600`, checksum, GPG
decryption test, and retention before uploading. Upload only the encrypted
artifact and checksum to the operator-approved off-VPS destination. Restore
into a new isolated PostgreSQL target, verify the checksum/key, row
relationships, and application queries. Never restore over production as a
first test.

## Rotation and session response

JWT, pairing, database, and backup-key rotation procedures are defined in
`P9.1-PRODUCTION-SECRET-AND-KEY-MANAGEMENT.md`. Use overlap only where the
documented protocol supports it; revoke sessions after compromise or an
operator-approved security event:

```sh
cd /opt/bmo/app/backend
# Run the approved operator-only session revocation procedure; no raw token is supplied.
```

No generic HTTP route may be used to rotate production keys or run migrations.

## Disable, rollback, and incident handling

Disable flags using the protected environment/configuration mechanism, restart
only the approved candidate service, and verify the sanitized health contract.
For failed migration, disk pressure, corruption, monitoring failure, or
compromise, follow the decision matrix in
`P9.1-PRODUCTION-ROLLBACK-RUNBOOK.md`. Stop before deleting data or rotating a
key if ownership/incident scope is unclear; escalate to the operator.
