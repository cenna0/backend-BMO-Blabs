## Artifact contract

The current operator script produces a PostgreSQL custom-format dump inside a
private container, streams it into GPG symmetric AES-256 encryption, writes a
temporary file in `/opt/bmo/backups/p9`, atomically renames it to
`p9-daily-<UTC>.dump.gpg` or `p9-weekly-<UTC>.dump.gpg`, then writes a SHA-256
sidecar over the final ciphertext. Files and sidecars are mode `0600`; the
directory is mode `0700`. No plaintext dump is retained. The checksum proves
the encrypted artifact bytes, not the plaintext database contents; restore
still validates GPG and application rows.

The first-canary finalized transfer set additionally requires a sanitized
`<backup-name>.manifest.json`. The backup tooling now emits and validates the
manifest after the encrypted artifact and checksum are complete. The manifest
implementation and focused tests are source-level evidence; exact production
basename activation and exact-copy restore remain future acceptance checks.
The Windows transfer, checksum, manifest, promotion, and GPG-readability
gates are verified. The Windows guide treats the manifest as mandatory and
rejects a set without it.

## Scheduler design

Use two host `systemd` service/timer pairs. This is a recommendation, not an
activated timer.

| Job | Asia/Jakarta schedule | Maximum runtime | Behavior |
|---|---|---:|---|
| Daily | `*-*-* 02:15:00 Asia/Jakarta` | 20 min | `P9_BACKUP_KIND=daily`; one shared `flock`; 3 retries with 30/120/300 s backoff |
| Weekly | `Sun *-*-* 02:45:00 Asia/Jakarta` | 30 min | `P9_BACKUP_KIND=weekly`; same lock; runs after daily window |

The service uses `UMask=0077`, `NoNewPrivileges=true`, a root-only secret
boundary, `TimeoutStartSec`, `OnFailure`, and `Persistent=true`. The lock is
held across dump, encryption, checksum, manifest, and retention, so daily and
weekly jobs cannot overlap. `Persistent=true` causes a
missed run to be attempted after boot; a lock or maintenance suppression
causes a nonzero result that is monitored rather than silently skipped.

A dedicated backup container is not recommended: it adds another runtime and
secret boundary without improving the current host scheduler. Cron remains an
acceptable operator fallback only if systemd is unavailable and the same lock,
timeout, and exit-status rules are preserved.

## Production monitoring signals

Record only timestamps, byte sizes, checksums, key version, outcome, and bounded
error codes:

| Signal | Warning | Critical / stop |
|---|---|---|
| Last successful local backup | Age > 26 h | Age > 50 h or two missed runs |
| Last manual PC pull | Older than 7 days | No verified Windows PC copy before a canary/migration or transfer age materially exceeds 7 days |
| Checksum | N/A | Any mismatch; quarantine artifact and do not delete prior good copy |
| GPG validation | N/A | Any decryption/authentication failure or wrong-key result during verification |
| Artifact size | >2× rolling median | Zero bytes, partial temp, or >2× database size without explanation |
| Retention | Count outside 7 daily/4 weekly | Newest valid artifact would be deleted or cleanup errors persist |
| Disk | <20 GB free | <10 GB free or staging exceeds 2 GB / 2× database size |
| Restore rehearsal | Local restore older than 7 days | Actual operator-PC-copy restore older than 31 days or fails application checks |
| Consecutive failures | 1 failed job | 2 failed jobs or checksum/encryption failure |

The external alert destination is `OPERATOR_APPROVAL_REQUIRED`; no email or
WhatsApp alert implementation is added. Beszel and systemd status are the
current monitoring surfaces. A local monitor cannot prove a whole-VPS outage.

## Backup execution order

1. Check the private PostgreSQL container is healthy and the data filesystem
   has headroom.
2. Acquire the shared lock and create a unique temporary filename.
3. Run `pg_dump --format=custom --no-owner --no-privileges` with a file-backed
   password inside the private container; never put `PGPASSWORD` in arguments.
4. Stream directly to GPG AES-256; do not write an intermediate plaintext dump.
5. Verify the encryption process and dump process both exit zero.
6. Set mode `0600`, atomically rename the artifact, calculate the ciphertext
   SHA-256, and atomically write its sidecar.
7. Validate checksum and GPG packet/decryption into a disposable isolated
   target before a first manual pull or after a key change.
8. Write and verify the sanitized manifest.
9. Apply local retention only after artifact, checksum, and manifest
   verification; preserve the newest valid local copy.
10. Emit a sanitized success record containing artifact name, size, checksum,
    manifest identity, and duration.

On any failure, remove only the named temporary output, leave the last known
good artifact, return nonzero, and trigger the monitoring policy. A partial
manual pull is not a valid PC copy and must not be treated as verified.

## Restore rehearsal

### Local weekly rehearsal

Restore the newest verified local artifact into a fresh isolated PostgreSQL
database with a new database name. The restore script rejects the primary
database name, validates the checksum before creating a target, decrypts via a
pipe, and runs `pg_restore --exit-on-error`. It must verify:

- migration rows and schema identity;
- row counts for all eleven P9.1 entities;
- zero orphan devices and zero broken populated `DevicePairing` references;
  `deviceId` may be `NULL` for non-claimed pairing lifecycle states, while a
  `CLAIMED` pairing must have a populated `(deviceId, userId)` reference that
  resolves to `Device(id, userId)`;
- `$argon2id$` password-hash prefixes without logging hashes;
- invitation, session, refresh, and pairing lifecycle states;
- `Asia/Jakarta`, Prudence, volume, and speed constraints;
- audit event count, event types, and absence of secret-bearing metadata;
- application login and `/api/v1/me` against the restored target;
- protected ops readiness and database recovery.

Destroy only the explicitly named disposable restore target after evidence is
captured. Do not target production or reuse its database name.

### Operator-PC monthly rehearsal

Restore one actual operator-PC copy at least monthly and after backup-key,
backup-tool, migration-system, or material PostgreSQL changes. Retain sanitized
evidence for artifact checksum, key version, restore duration, row checks,
application login, and data-loss boundary. A PC copy that cannot be restored is
not a backup for acceptance purposes.

### Exact PC-copy return staging

The accepted restore input is only the exact three-file set verified under the
Windows `verified` directory. Return it to this dedicated VPS path with the
approved SSH identity, strict known-hosts checking, and three explicit
filenames:

```text
/opt/bmo/p9.1-restore-tests/incoming/<backup-id>
```

The staging root, `incoming`, and per-backup directory are
`bmo-admin:bmo-admin` mode `0700`; each staged file is a regular non-symlink
owned by `bmo-admin:bmo-admin` mode `0600`. This path is separate from
`/opt/bmo/p9.1-backups/daily`. Reject missing or extra members, symlinks,
unexpected modes/sizes, malformed sidecars, checksum mismatch, or manifest
mismatch. Do not overwrite an existing set or use a wildcard transfer.

Run `npm run p9:restore:validate-config -- <staged-set-directory>` through the
durable Node 22 runner before any restore. The preflight performs no Docker,
PostgreSQL, GPG, target, or artifact side effect. The real restore performs a
no-output GPG authentication pass before creating the explicitly named fresh
target, then streams a fresh GPG process into `pg_restore`. Successful targets
remain for evidence; failed targets are cleaned only by the exact-target rule.
Staged files remain until evidence and cleanup pass. The candidate `/tmp`
PostgreSQL password-file path is rehearsal-only.

## Corruption and wrong-key behavior

Corrupted ciphertext must fail checksum before target creation. A wrong key or
passphrase must fail GPG authentication and must not create or overwrite a
database. A partial output, missing sidecar, stale checksum, or failed
`pg_restore` is invalid and never enters retention. The current isolated review
verified checksum rejection, wrong-passphrase rejection, atomic output, and
fresh-target restore; the Windows exact-copy transfer and GPG-readability gates
are now verified. The exact PC-copy return and restore remain future canary
gates; no restore target has been created in this checkpoint.
