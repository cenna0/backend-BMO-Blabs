**Status:** approved first-canary design; no real production secret exists and
no step in this guide has been executed.

This is the practical handoff guide. The deeper rules and rationale are in

The access table is in

[`P9.1-WINDOWS-OFF-VPS-BACKUP-GUIDE.md`](P9.1-WINDOWS-OFF-VPS-BACKUP-GUIDE.md).

## What the secrets do

- **JWT signing key:** proves that a P9.1 access token was signed by BMO.
- **Pairing HMAC key:** protects six-digit pairing codes without storing the
  code itself.
- **PostgreSQL owner password:** break-glass database administration only.
- **PostgreSQL migration password:** applies reviewed Prisma migrations only.
- **PostgreSQL application password:** normal Backend database access only.
- **PostgreSQL backup password:** read-only `pg_dump` access only.
- **PostgreSQL restore password:** isolated restore operations only.
- **Backup encryption material:** encrypts local backup artifacts; it is not a
  database credential.
- **Invitation secret:** one-time registration value displayed once; only its
  hash is stored.
- **SSH/Tailscale access:** private operator access to the host, managed as a
  host-access concern rather than a P9.1 container secret.

The BMO operator owns all of them. Audio, Hermes, Caddy, mobile clients, and
the operator PC must not receive the P9.1 service secrets. The operator PC may
hold encrypted backup artifacts and an encrypted recovery archive, never
plaintext database dumps or plaintext recovery secrets.

## Where they go

The planned host root is `/opt/bmo/secrets/p9.1/`, outside the repository and
Docker build context. Services receive only read-only mounts under
`/run/secrets/`. The logical tree and permission rules are authoritative in the
deep technical document; final numeric UID/GID and mode values are recorded
only after the actual production image and container access are verified.

No global environment file is used. No production secret is placed in a
Compose literal, image layer, command argument, shell history, log, health
response, audit event, or evidence file.

For the first canary, the operator PC is Windows. PowerShell is canonical;
Tailscale provides the private path; Windows OpenSSH `scp.exe` transfers the
three exact files; `Get-FileHash -Algorithm SHA256` verifies ciphertext; and
Gpg4win/GnuPG performs interactive readability verification. The real Windows
installation, SSH key ACL check, transfer, and exact-copy restore remain
pending evidence.

## Provisioning checklist

**FUTURE PRODUCTION ACTION — DO NOT RUN DURING READINESS.** This checklist is
performed only after a separate canary approval and a private maintenance
window.

- [ ] Confirm the exact final main SHA, approved image, private network, and
      rollback anchor.
- [ ] Confirm the operator owns the provisioning and recovery records.
- [ ] Create `/opt/bmo/secrets/p9.1/` as root outside Git.
- [ ] Check the actual UID/GID of Backend, PostgreSQL, and each one-shot
      migration/backup/restore process.
- [ ] Generate each value from the OS CSPRNG directly into its intended file;
      do not type or print a value.
- [ ] Set a root-owned parent and the least group-readable mode that the
      verified consuming process can actually read.
- [ ] Prohibit symlinks, hard links, world access, repository paths, and
      recursive ownership changes outside the secret tree.
- [ ] Mount only the required files read-only at `/run/secrets/<name>`.
- [ ] Confirm the container sees the file and cannot write it, without printing
      contents.
- [ ] Confirm PostgreSQL has no undocumented default password.
- [ ] Confirm JWT, pairing, and app-password startup validation fails closed.
- [ ] Record only identifiers, versions, owners, modes, byte counts, mounts,
      and pass/fail outcomes.
- [ ] Place an encrypted recovery archive on the operator PC and one separate
      offline encrypted copy. Do not store either recovery secret in plaintext.

## Safe validation checklist

These checks expose metadata only. They are templates for the future operator
procedure and are not executed by this branch:

```sh
# FUTURE PRODUCTION ACTION — DO NOT RUN DURING READINESS
set -eu
root=/opt/bmo/secrets/p9.1
test -d "$root"
find "$root" -xdev -type l -print -quit | (! grep -q .)
find "$root" -maxdepth 3 -type f -printf '%M %u:%g %s %p\n'
```

Expected output is a list of approved secret paths with approved owner/group,
non-world-readable modes, and nonzero sizes. It must not contain file content,
environment dumps, credentials, or a secret fingerprint.

For each service, validate the read-only mount inside the private candidate
without printing it. A successful check proves file existence, expected byte
count, and readable permission; it does not prove a secret value is safe to
display. Keep the result as sanitized evidence.

## Rotation checklist

### Normal JWT rotation

- [ ] Back up and verify the database and recovery material.
- [ ] Disable P9.1 public flags and stop new authentication traffic.
- [ ] Create version 2 in the protected directory.
- [ ] Switch the active version and restart only the approved Backend.
- [ ] Verify new login and protected requests.
- [ ] Verify old access tokens fail; the normal token lifetime is 900 seconds.
- [ ] Keep valid opaque refresh sessions unless this is a security incident;
      they can rotate and receive new version-2 access tokens.
- [ ] Remove version 1 only after successful evidence and retain no stale
      plaintext copy.

The current design has no dual-`kid` overlap. A future overlap requires a
separate implementation review and must not exceed the token lifetime plus an
approved clock margin.

### Pairing HMAC rotation

- [ ] Disable pairing issuance.
- [ ] Revoke all active `ISSUED` pairing codes.
- [ ] Install version 2 and restart the approved Backend.
- [ ] Verify old claims fail and new codes work.
- [ ] Wait through the ten-minute code lifetime before normal issuance.
- [ ] Record the audit event without code values.

### PostgreSQL credential rotation

- [ ] Stop the relevant one-shot job or enter an approved maintenance window.
- [ ] Use a staged least-privilege replacement app role where uninterrupted
      Backend operation is required.
- [ ] Update only the protected file for the intended consumer.
- [ ] Establish a fresh connection and verify the expected least privilege.
- [ ] Drain old connections, restart/reconnect the consumer, then revoke the
      old role/password.
- [ ] Verify the old credential no longer works and the new one does.

The Backend must never receive owner, migration, backup, or restore passwords.

### Backup-key rotation

- [ ] Create version 2 in protected storage.
- [ ] Encrypt a new backup with version 2 and verify checksum, manifest, and
      isolated restore.
- [ ] Update the PC and offline recovery sets.
- [ ] Retain version 1 until every version-1 artifact expires or is re-encrypted
      and verified.
- [ ] Retire version 1 only after the recovery inventory is complete.

## Recovery checklist

- [ ] Identify the exact encrypted artifact, checksum, and sanitized manifest.
- [ ] Use the operator PC copy first; verify the checksum before any restore.
- [ ] Use the encrypted recovery archive, never a plaintext key file.
- [ ] Restore only to a fresh, explicitly named isolated PostgreSQL target.
- [ ] Verify migration state, row counts, ownership, password-hash prefixes,
      settings, audit events, login, and `/api/v1/me`.
- [ ] Preserve sanitized evidence and destroy only the explicitly named
      disposable target after review.
- [ ] Never restore over production as the first recovery test.

If the PC is lost, use the additional offline encrypted copy. If both copies
and all recovery material are lost, the affected encrypted backups are not
recoverable; record the incident and do not invent a successful restore claim.

## Emergency checklist

For any suspected exposure:

1. Stop the affected P9.1 feature or one-shot operation.
2. Do not copy the suspected value into a ticket, shell command, or log.
3. Preserve sanitized timestamps, service identity, source SHA, and audit IDs.
4. Revoke sessions or pairing codes where applicable.
5. Rotate the affected secret and any dependent credential.
6. Verify startup, least privilege, health sanitization, and recovery.
7. Follow the individual procedures in
   [`P9.1-PRODUCTION-SECRET-INCIDENT-RUNBOOKS.md`](P9.1-PRODUCTION-SECRET-INCIDENT-RUNBOOKS.md).

## Troubleshooting

**Permission denied or unreadable mount:** stop the service; inspect only owner,
group, mode, mount source/target, and effective container UID/GID. Do not make
the file broadly readable. Correct the verified service group or mount, then
restart in a private maintenance window.

**Missing file or startup failure:** leave the feature disabled. Confirm the
exact versioned path and file metadata. Never substitute a development value or
put the secret on the command line.

**Wrong credential after rotation:** stop new traffic, preserve the old
credential only in its approved recovery boundary, verify the new role and
fresh connection, and roll back only if compromise is not suspected.

**Lost recovery key:** stop claiming the backup is restorable. Check the
operator PC and separate offline inventory. If no valid recovery copy exists,
record the loss as an unrecoverable backup incident.

## Glossary

- **CSPRNG:** operating-system cryptographic random-number generator.
- **HS256:** HMAC-SHA-256 signing mode used for P9.1 access tokens.
- **HMAC:** keyed hash used to protect a value without storing it in plaintext.
- **GPG:** the encryption tool used for first-canary backup artifacts.
- **Least privilege:** granting only the operations required for one job.
- **Read-only mount:** a container file mount that cannot be written by that
  container.
- **Rotation:** replacing an active secret while preserving the intended
  service behavior and evidence.
- **Revocation:** making an existing credential, session, code, or role no
  longer valid.
- **Escrow:** a separately protected recovery copy held for disaster recovery.
- **RPO:** the maximum acceptable amount of data loss measured in time; weekly
  manual PC pulls imply an approximately seven-day worst case for off-VPS
  recovery.
