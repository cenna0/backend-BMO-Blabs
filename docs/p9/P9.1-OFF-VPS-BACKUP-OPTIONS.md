# P9.1 Off-VPS Backup Destination

**Decision status:** `LOCKED_FOR_FIRST_CANARY — WINDOWS / POWERSHELL / TAILSCALE / SCP`

## Approved destination

The initial P9.1 disaster-recovery destination is the operator-owned personal
computer. Transfer is a manual operator pull from the VPS. The first canary
does not require Backblaze B2, Cloudflare R2, Google Drive, a NAS, or a second
server.

No account, remote bucket, upload, or production credential is created by this
readiness branch. The operator PC is Windows. PowerShell, the Windows OpenSSH
`scp.exe` client, the private Tailscale path, and Gpg4win/GnuPG are the locked
first-canary tools. The exact Tailscale machine identity, remote backup path,
Windows destination path, and approved SSH key remain provisioning-time checks.

The complete Windows procedure is
[`P9.1-WINDOWS-OFF-VPS-BACKUP-GUIDE.md`](P9.1-WINDOWS-OFF-VPS-BACKUP-GUIDE.md).

## VPS backup contract

Create encrypted PostgreSQL custom-format backups automatically on the VPS:

- daily at 02:15 Asia/Jakarta;
- seven daily encrypted copies;
- four weekly encrypted copies;
- SHA-256 sidecar for the final encrypted artifact;
- sanitized manifest containing database identity, timestamp, migration state,
  format, artifact name/size, and checksum;
- atomic output and restrictive permissions;
- no persistent plaintext database dump.

The backup artifact, checksum, and manifest are separate transfer units. A
failed dump, encryption, checksum, or manifest write must not trigger cleanup
of the newest valid backup.

## Manual operator pull

The operator must pull a verified backup to the personal computer:

- at least once per week;
- before a production database migration;
- after a successful production migration;
- before a high-risk deployment;
- after P9.1 production verification.

Transfer only the encrypted backup artifact, checksum file, and sanitized
manifest. Never transfer or expose plaintext dumps, PostgreSQL credentials, JWT
signing keys, pairing HMAC keys, or raw application secrets.

The transfer is a pull from the VPS, initiated by the operator through the
verified Tailscale path using Windows `scp.exe`. PowerShell performs SHA-256
verification with `Get-FileHash -Algorithm SHA256`; Gpg4win/GnuPG performs
interactive encrypted-artifact readability verification. The canonical guide
uses exact paths, no wildcards, no recursive SCP, and explicit SSH host-key
checking. Shell history must not contain secrets or passphrases.

## PC retention

The personal computer must retain at minimum:

- the four latest weekly backups;
- three manually protected milestone backups.

Milestone backups are outside ordinary weekly rotation and must not be deleted
by routine cleanup. Their filenames and manifest metadata must identify the
milestone without exposing credentials or database contents.

## Verification on every pull

Before considering a manual transfer successful, verify:

1. the artifact exists and its size is plausible;
2. the SHA-256 checksum matches the sidecar;
3. the encrypted artifact is readable with the approved recovery key;
4. the sanitized manifest identifies database, timestamp, migration state, and
   backup format;
5. no plaintext dump, credential, token, or raw secret is present.

Store only sanitized verification evidence. Do not copy the recovery key into
the backup directory, Git, logs, evidence, Docker image layers, or shell
history.

## Restore rehearsal before canary approval

Before P9.1 production canary approval:

1. create an encrypted backup on the VPS;
2. manually pull that exact artifact, checksum, and manifest to the operator PC;
3. verify the checksum on the PC;
4. restore from that exact PC copy into a fresh isolated database;
5. verify schema and migration state;
6. verify row counts and ownership relationships;
7. run login and `/api/v1/me` application checks;
8. preserve sanitized evidence.

Repeat an actual PC-copy restore at least monthly and after backup-key,
backup-tool, migration-system, or material PostgreSQL changes. A local VPS
restore does not satisfy this gate.

## Recovery-point consequence

Weekly manual transfer produces a worst-case disaster-recovery RPO of
approximately seven days. Daily local backups provide faster recovery only
while the VPS and its disk remain available. The operator accepts this
limitation for the initial P9.1 scale. One additional offline recovery copy is
required before final P9.1 production verification.

## Windows transfer state and key ownership

The operator is the ultimate backup-key owner. Runtime encryption material is
restricted to approved production secret storage, and the recovery copy is
held on the operator PC in an encrypted recovery archive. Production key
generation, exact Tailscale identity, exact Windows path, and actual SSH key
ACL verification remain pending execution. No production secret is generated
by this task. The Windows transfer procedure is locked, but its real transfer,
checksum, GPG, and restore evidence is not yet complete.

## Deferred alternatives

Backblaze B2, Cloudflare R2, Google Drive, NAS, and a second server remain
possible later destinations, but none is required or selected for the first
canary. Their prior comparison is retained only as historical analysis; it
does not override this locked operator-PC decision.
