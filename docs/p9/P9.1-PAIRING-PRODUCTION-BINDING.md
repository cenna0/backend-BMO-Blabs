# P9.1 Pairing Production Binding

## Verdict

P9.1 backend pairing behavior is implemented and independently reviewed:
authenticated-user issuance, six-digit HMAC-protected code, 600-second TTL,
single use, bounded attempts, new-code invalidation, atomic claim, replay
rejection, ownership isolation, unpair revocation, and audit redaction all
pass isolated tests.

The production hardware identity boundary is not complete. The current issue
route is authenticated-user scoped and accepts hardware identity during claim;
it does not yet prove that an unowned physical device is the device associated
with the displayed code before issuance/display. Therefore hardware binding is
`OPERATOR_APPROVAL_REQUIRED`; pairing must remain feature-disabled in a
production canary until the binding is verified. This is not a reason to change
Hardware Contract v1.0.5.

## Required production design

### Device credential

Each physical BMO receives a unique 32-byte random bootstrap credential during
manufacturing or an operator-controlled provisioning step. It is stored in
device-protected storage, never in firmware source, logs, mobile state, or the
pairing response. Backend stores only a salted verifier or keyed digest and a
non-secret hardware identity. The credential is scoped to:

- device authentication and pairing bootstrap only;
- no user impersonation, database access, or operator route;
- no ability to claim a device without a valid authenticated mobile user and
  an unexpired pairing challenge.

The exact provisioning owner, manufacturing process, and recovery secret are
`OPERATOR_APPROVAL_REQUIRED`. The existing static P7 `DEVICE_ID`/`DEVICE_TOKEN`
handoff is not sufficient for a multi-device owned/unowned registry.

### Additive transport flow

The safe additive flow, subject to hardware/mobile review, is:

```text
Unowned device → existing authenticated device channel with bootstrap proof
               → Backend verifies device identity and unowned state
Authenticated mobile → POST /api/v1/pairing/challenges
                     → Backend binds challenge to user + authenticated device
                     → device receives/display-binding instruction over its channel
Mobile → POST /api/v1/pairing/:id/claim
       → Backend locks challenge/device/user and creates one owner atomically
       → Backend rotates device credential and invalidates challenge
```

If the existing v1.0.5 WebSocket authentication cannot carry this additive
identity proof without changing its contract, use a new versioned backend
bootstrap endpoint/channel and keep v1.0.5 unchanged. Do not overload
`audio_ready`, `display_status`, or another request-bound event.

### Display binding

The code must be displayed only by the authenticated physical device that
requested or received the challenge. Backend associates a challenge with the
verified device identity, records an opaque display session ID, and invalidates
that session when a new code is issued, the code expires/revokes, ownership is
claimed, or the device disconnects beyond the defined short window. Mobile
never receives a code belonging to another user's device. A status poll returns
only sanitized lifecycle state, not the code after one-time issuance.

## State and race rules

| State | Allowed transition | Security rule |
|---|---|---|
| `ISSUED` | `CLAIMED`, `EXPIRED`, `REVOKED`, `INVALIDATED`, `FAILED` | Code is hash-only, TTL 600 s, max 5 attempts |
| `CLAIMED` | terminal | One owner and one device credential transaction |
| `EXPIRED` | terminal | Claim rejects even if code matches |
| `REVOKED` | terminal | Explicit operator/user revoke |
| `INVALIDATED` | terminal | New challenge or ownership transition |
| `FAILED` | terminal | Attempt limit or security failure |

Issuance locks the authenticated user and invalidates prior active challenges.
Claim locks the user/challenge/device identity and uses a timing-safe digest
comparison. Two concurrent claimers can produce at most one `CLAIMED` device;
the loser receives a generic conflict. A second user receives the same safe
not-found/invalid result and cannot enumerate a pairing or device.

## Post-claim and recovery

- Claim creates one active owner, one hashed device credential, default-device
  settings if it is the user's first device, and an audit event.
- Unpair revokes device-bound sessions, refresh tokens, outstanding challenges,
  device access, and repairs the default-device invariant.
- Credential rotation invalidates the old credential atomically and requires an
  out-of-band device provisioning action.
- Factory reset clears device-held credentials and requires a new operator-
  approved enrollment path; it does not silently transfer ownership.
- Lost device: revoke device and sessions; issue a replacement only through a
  new authenticated challenge and verified hardware identity.
- Device replacement: old hardware remains revoked in audit history; hardware
  ID uniqueness prevents silent reuse.

## Rate limits and audit

Limit challenge issue/claim to 10 per 15 minutes per normalized client IP, plus
authenticated-user/device controls. Add a separate bounded per-device failed
claim counter. Audit `PAIRING_REQUESTED`, `PAIRING_INVALIDATED`,
`PAIRING_CLAIMED`, `PAIRING_FAILED`, `PAIRING_EXPIRED`, `PAIRING_REVOKED`, and
`DEVICE_UNPAIRED` with opaque IDs, outcome, request ID, and attempt count only.
Never record the code, credential, digest, or raw hardware secret.

## Feature binding decision

During a future P9.1 canary:

- `P9_AUTH_ENABLED=true` only for the approved operator/invite cohort;
- `P9_PAIRING_ENABLED=false` unless the hardware identity/display proof has
  passed the pairing matrix;
- no public route or Caddy path is added for device bootstrap before that proof;
- settings and authentication can be canaried independently of pairing;
- mobile UX remains a contract/state dependency, not a screen-design decision.

The hardware and mobile owners must approve the credential provisioning,
display binding, replacement, and recovery behavior. No firmware or Hardware
Contract change is made here.
