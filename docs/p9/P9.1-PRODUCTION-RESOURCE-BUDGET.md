# P9.1 Production Resource Budget

**Status:** proposed canary limits; values are not permanently locked.

## Evidence boundary

The host has approximately 8.3 GiB RAM and no swap. P8 Audio is the dominant
consumer, with an observed peak near 4.55 GiB and earlier host minimum
`MemAvailable` near 2.6–2.9 GiB. The isolated P9.1 review measured PostgreSQL
peak near 79.1 MiB under a 768 MiB cgroup, candidate Backend near 290.5 MiB
under 512 MiB, and Argon2 workload peak near 85.5 MiB. These are evidence, not
permission to remove limits or overlap Audio replacements.

## Proposed first-canary limits

| Component | Proposed limit / concurrency | Rationale and gate |
|---|---:|---|
| PostgreSQL | `768 MiB`, no swap, `1.0 CPU`, PID `128` | Locked initial target and isolated margin; remeasure cgroup-wide |
| PostgreSQL max connections | `20` | Matches locked pool target and bounded candidate pressure test |
| Prisma pool | `5` connections, 2 s connect timeout, 10 s transaction timeout | Prevents Backend from consuming all DB slots |
| Backend candidate | `512 MiB`, `1.0 CPU`, PID `128` | Candidate evidence below cap; must be remeasured with P9 routes |
| Audio | Preserve current P8 `5 GiB`, `4 CPU`, PID `128` | Do not alter Audio behavior or overlap a second Audio container |
| Hermes | Preserve current host allocation/runtime | Existing production baseline; no P9 ownership |
| Argon2 | At most `2` concurrent password operations in canary traffic; bounded queue | Four-concurrent evidence passed but no swap and Audio dominates memory |
| Backup | One dump/encryption/upload job; no overlap | Prevents disk and CPU spikes |
| Migration | One operator process only; no application writes before ready | DDL/lock behavior is first-database controlled rollout |

The current P9 source does not add a runtime Argon2 semaphore; the canary must
enforce the two-operation cohort through traffic limits and stop conditions, or
implement a separately reviewed guard before broader traffic. Do not add Redis
or a general job queue for this gate.

## Stop thresholds

Stop the canary and preserve evidence immediately when any critical threshold is
hit:

| Signal | Warning | Stop / rollback |
|---|---:|---:|
| Host `MemAvailable` | `<2.5 GiB` for 60 s | `<2.0 GiB`, any production degradation, or no recovery after traffic stop |
| PostgreSQL cgroup memory | `>75%` for 5 min | `>95%`, OOMKilled, or restart |
| Backend cgroup memory | `>80%` for 5 min | `>95%`, OOMKilled, or restart |
| Kernel OOM counter | record baseline | any positive delta |
| Production restart count | record baseline 0 | any increase |
| DB connections | `>=18/20` | `20/20`, refusals, or pool queue >5 s |
| DB query latency | p95 >250 ms | p95 >500 ms for 5 min or transaction errors |
| Backend event loop | p95 >100 ms | p95 >250 ms or request timeout spike |
| Disk free | `<20 GB` | `<10 GB`, database filesystem error, or backup staging runaway |
| Backup staging | >1 GiB or 2× DB size | >2 GiB, partial-output accumulation, or no cleanup |
| Public health | one isolated failed probe | two consecutive failures, legacy voice regression, or 503 rate >1% |

The 2 GiB host reserve is intentionally above the absolute zero-free-memory
boundary because the host has no swap and Audio can use several GiB. The
threshold is a canary stop rule, not a claim that the host can safely run at
that level indefinitely. The operator must recapture a kernel-OOM baseline
immediately before a future canary.

## Measurement protocol

Measure cgroup `memory.current`, `memory.peak` (or Docker equivalent), all
PostgreSQL processes, container restarts/OOMKilled, CPU, PIDs, connections,
database size, and host `MemAvailable`. Record idle, migration, auth/Argon2,
connection pressure, backup, restore, and restart phases separately. Use
bounded concurrency and stop on the thresholds above. Do not load-test public
production or overlap production Audio replacements.
