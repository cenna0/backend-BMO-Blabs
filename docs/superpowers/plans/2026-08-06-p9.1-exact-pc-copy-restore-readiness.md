# P9.1 Exact PC-Copy Restore Readiness Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use test-driven-development and verification-before-completion while implementing this plan.

**Goal:** Harden the P9.1 restore workflow so only a revalidated exact three-file Windows PC copy can be restored into one explicitly named fresh disposable target, with GPG authentication before target creation, streamed decryption, sanitized diagnostics, deterministic cleanup, and side-effect-free preflight.

**Architecture:** Add a shared restore configuration boundary around the dedicated restore staging path, protected-file contracts, exact-set/checksum/manifest validation, and safe target naming. Reuse the Compose environment construction and child-process sanitization boundary. Keep restore orchestration dependency-injectable for deterministic tests, with a no-output GPG authentication pass before target creation and a separate streamed GPG-to-`pg_restore` execution path. Add pure/read-only evidence helpers for the later acceptance rehearsal.

**Tech Stack:** TypeScript, Node.js 22, Vitest, Docker Compose, PostgreSQL client tools, GnuPG, Prisma.

### Task 4: Harden Compose, GPG, restore execution, and cleanup

**Files:** `backend/src/p9/operator/compose.ts`, `backend/src/p9/operator/restore.ts`.

- Propagate the validated PostgreSQL password-file path into every Compose invocation.
- Add sanitized process categories for configuration, target checks/creation/cleanup, GPG authentication/decryption, and actual `pg_restore` failures.
- Validate Compose interpolation, authenticate the artifact with GPG to `/dev/null`, prove the target is absent, create only the exact target, then stream a fresh GPG decryption process into custom-format `pg_restore` with `--no-owner`, `--no-privileges`, and `--exit-on-error`.
- On post-creation failure, clean only the exact target and report cleanup separately; retain successful targets for evidence and never create plaintext dumps.
