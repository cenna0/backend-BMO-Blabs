# P9.1 Foundation Implementation Plan

> **For agentic workers:** Execute this plan task-by-task with review checkpoints. Keep `main`, production Compose, Audio Service behavior, and Hardware Contract v1.0.5 unchanged.

**Goal:** Implement and validate the isolated P9.1 PostgreSQL, Prisma, authentication, user/device, pairing, settings, audit, backup, restore, and persistence foundation.

**Architecture:** Extend the existing TypeScript Backend behind `P9_ENABLED=true`; all P9 database access goes through repositories and domain services. The candidate uses a separate private Compose project with PostgreSQL and an isolated Backend process; production never receives the P9 environment flag or database network.

**Tech Stack:** Node 22, TypeScript/Express 5, Prisma 7.9.1, `@prisma/adapter-pg` 7.9.1, `pg` 8.22.0, Argon2id via `argon2` 0.45.1, JWT via `jose` 6.2.8, existing Zod 3.25.76, `express-rate-limit` 8.6.1, PostgreSQL 16.10 Alpine, Docker Compose, Vitest, Supertest, and `pg_dump`/`age` tooling.

## File map

Create the following focused units in `backend/`:

- `prisma/schema.prisma`, `prisma.config.ts`, `prisma/migrations/`, and `prisma/seed.ts` — P9.1 schema, migration history, and explicit test fixtures only.
- `src/p9/config.ts`, `src/p9/errors.ts`, `src/p9/types.ts`, `src/p9/crypto.ts`, `src/p9/validation.ts` — P9 configuration, typed errors, cryptographic primitives, and Zod request schemas.
- `src/p9/db/client.ts`, `src/p9/db/repositories.ts`, `src/p9/db/transaction.ts` — Prisma adapter, query boundaries, and transaction helpers.
- `src/p9/services/audit.service.ts`, `invitation.service.ts`, `auth.service.ts`, `session.service.ts`, `user.service.ts`, `device.service.ts`, `pairing.service.ts`, `settings.service.ts` — policy and state transitions.
- `src/p9/http/auth.route.ts`, `device.route.ts`, `pairing.route.ts`, `settings.route.ts`, `ops.route.ts`, `middleware.ts`, `router.ts` — versioned P9 API and redacted error mapping.
- `src/p9/operator/create-invitation.ts`, `src/p9/operator/backup.ts`, `src/p9/operator/restore.ts` — operator-only invitation and backup/restore commands.
- `src/p9/index.ts` — feature-gated runtime composition.
- `p9.1-compose.yml`, `.env.p9.1.example`, `scripts/p9.1-*.sh` — isolated database/runtime and operational commands.
- `tests/p9/*.test.ts`, `tests/p9/*.integration.test.ts`, and `tests/p9/helpers/*` — unit, API, race, persistence, security, and operational tests.
- `docs/p9/P9.1-IMPLEMENTATION-PLAN.md`, `P9.1-ACCEPTANCE-EVIDENCE.md`, `P9.1-ROLLBACK.md`, and `P9.1-THREAT-ASSUMPTIONS.md` — implementation decisions and sanitized evidence.

Modify only these existing Backend integration points:

- `backend/package.json`, `package-lock.json`, `tsconfig.json` — dependencies, scripts, and generated client inclusion.
- `backend/src/config/env.ts` — optional P9 feature/config fields with safe disabled defaults.
- `backend/src/server.ts` — mount P9 router only when `P9_ENABLED=true` and close the P9 Prisma client on shutdown.
- `backend/src/http/health.route.ts` only if a non-breaking candidate readiness hook is needed; existing `/health`, `/livez`, and `/readyz` response/status behavior must remain unchanged.

Do not modify `audio-service/**`, `docs/hardware-contract/**`, `docker-compose.yml`, existing voice routes, existing WebSocket events, Caddy/DNS, or production runtime files.

## Checkpoint policy

Each checkpoint is a separate commit and must pass its focused tests plus `git diff --check`. The checkpoints are:

`A database foundation` → `B schema/migrations` → `C invitations/auth` → `D sessions` → `E users/settings` → `F devices/pairing` → `G audit` → `H backup/restore` → `I tests/operations/evidence`.

Before each commit, run the focused command named in the task and inspect the diff. No P9.2–P9.6 schema or runtime is allowed.
