# P9.1 Restored-Target Application Acceptance Tooling Design

## Goal

Provide repository-supported, testable tooling for running the real P9 backend
against an existing `bmo_restore_*` database without repointing the candidate
or production runtime. This checkpoint prepares the tooling only; it does not
start the runtime, create a fixture, or perform login acceptance.

## Architecture

The tooling has four boundaries:

1. A pure configuration layer validates a safe restore database name, the
   candidate private network, loopback-only HTTP exposure, dedicated runtime
   identity, disabled migrations, and protected secret-file metadata before
   any Docker or database side effect.
2. A disposable Docker runtime layer launches the existing candidate backend
   image as a second container on `bmo-p9-1_p9_private`. It mounts the
   checked-out compiled `dist/src` read-only so the exact candidate image can
   carry the acceptance tooling without rebuilding or repointing the candidate.
   It publishes only a caller-selected host loopback port, never creates
   PostgreSQL, and always constructs the backend database URL from the supplied
   restore database and mounted password-file path.
3. A fixture layer runs the real Argon2id password helper in a disposable
   backend-image command. It creates a synthetic user, password credential,
   password identity, and user settings only in the validated restore target.
   The host keeps an operator-owned `0600` canonical manifest containing only
   cleanup identifiers; stateful workers consume a separate `1000:1000`
   `0600` file on container-local tmpfs and return structured state captured by
   the host for atomic validation/update.
4. An acceptance/evidence layer performs future HTTP checks without printing
   secrets, captures aggregate database deltas by phase, and requires an
   application-reported `current_database()` identity to equal the restore
   target.

## Runtime safety

The runtime launcher accepts an explicit `P9_ACCEPTANCE_DATABASE` and rejects
`bmo`, empty values, and names outside the repository's `bmo_restore_*` policy.
It requires `bmo-p9-1_p9_private`, rejects production/candidate container
identities, and uses a distinct deterministic acceptance container name. The
only server command is the existing candidate server; no migration command is
available to the launcher, and migration mode is explicitly set to disabled.
The launcher checks that the named database already exists before starting and
uses sanitized diagnostics for all process failures.

The host binding is `127.0.0.1`; PostgreSQL remains private and unpublished.
The existing candidate PostgreSQL and backend services are never recreated,
restarted, or repointed. Stop removes only the named acceptance container.

Pre-fixture aggregate evidence is intentionally manifest-free: it only reads
database counts and must not create or mount an empty fixture state file.
Fixture creation writes a pending canonical manifest before the worker starts;
the runtime copy is materialized from that manifest and is destroyed with the
worker. A successful worker returns the completed state through captured
structured output, which the host validates against the pending run identity
and atomically installs. If the worker dies after creating rows, the pending
manifest remains for exact cleanup by synthetic email/provider subject; if no
matching row exists, cleanup removes only the pending manifest. Ambiguous or
malformed state fails closed.

## Credential and fixture safety

The acceptance password is supplied only through an operator-provisioned,
absolute, regular, non-symlink file with mode `0600`, safe ownership, and
runtime readability. The tooling reads it only in memory for the real
`hashPassword()` helper or one future login request. It never logs, hashes for
evidence, encodes, prints, or passes the value as a command argument.

Fixture creation generates a collision-resistant run identifier and synthetic
email/provider subject, creates the required user/auth/settings rows in one
transaction, and stores only the run identity and created user identity in the
protected host manifest. Cleanup verifies that identity, synthetic marker, owned
relations, and absence of unexpected device/pairing ownership before deleting
fixture audit events and the fixture user; ambiguous ownership fails closed.

## Evidence and failure handling

Aggregate counts are captured at the restored-target baseline, after fixture
creation, after exactly one future login, and after explicit cleanup. Expected
deltas are categorized as fixture creation, login session/refresh/audit
effects, and cleanup. Any unexpected table delta fails acceptance. Existing
restore integrity checks remain read-only and include migration state, schema
identity, pairing references, ownership, Argon2id format, and audit metadata.

Runtime-start failure leaves the restore target untouched and removes only
runtime residue. Fixture failure invokes exact partial cleanup. Login failure
retains sanitized evidence and does not automatically delete the restored
database or fixture. Successful acceptance retains the restored target and
staged PC copy; runtime stop and fixture cleanup are explicit operations.

## Test and documentation strategy

Pure unit tests cover target/network/identity/port/migration/file validation,
Docker argument construction, fixture ownership and cleanup, secret redaction,
acceptance response sanitization, target identity, mutation categorization,
and unexpected-delta failure, host/runtime state ownership, atomic
synchronization, pending-state recovery, and explicit CLI entrypoints. Tests
use synthetic files and data only. The documented npm scripts invoke the
explicit CLI entrypoint; compiled-file invocation is not an operator
requirement.

P9.1 documentation will state:

- database-level restore is verified;
- isolated application-acceptance tooling is ready but real acceptance has not
  executed;
- the runtime never repoints the primary candidate;
- the synthetic fixture exists only in a disposable restore target;
- no existing password is reset and no authentication bypass exists;
- migrations are disabled and the restored target is never auto-dropped;
- the candidate `/tmp` PostgreSQL password path remains rehearsal-only.
