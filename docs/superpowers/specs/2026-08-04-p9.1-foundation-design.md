# P9.1 Foundation Design

**Status:** approved for isolated implementation on `feat/p9.1-foundation`
**Base:** `82721f0637dfd4a5207e4707ccbd4d5696704964`

## Goal and boundary

Build an isolated, private P9.1 application foundation behind the existing
Backend boundary. It owns PostgreSQL persistence, invite-only email/password
identity, short-lived access tokens, rotating opaque refresh sessions, device
ownership and pairing, settings, audit events, database readiness, migrations,
encrypted local backups, and restore rehearsal. The existing voice routes,
WebSocket events, Audio Service, Hermes integration, production Compose
project, and Hardware Contract v1.0.5 remain unchanged.

P9.2–P9.6 entities and runtime behavior are deliberately excluded. The only
open decisions carried forward are the off-VPS backup destination, production
email/password-reset operations, and final mobile UX.

## Approaches considered

1. **Feature-gated extension of the existing TypeScript Backend (selected).**
   Add a P9 runtime composition that is enabled only by `P9_ENABLED=true` in
   the candidate environment. Put all database access behind repositories and
   services, and leave the existing voice composition intact when the flag is
   false. This preserves current conventions and makes production non-impact
   testable.
2. **Separate P9 HTTP service.** This would maximize process isolation, but it
   would duplicate Backend configuration, error handling, health conventions,
   and deployment concerns for a foundation that is already owned by Backend.
3. **Direct Prisma use in route handlers.** This is shorter initially, but it
   would spread ownership policy, transaction boundaries, and redaction logic
   across HTTP code and make race/security testing harder. It is rejected.

## Technology choices

- PostgreSQL: official `postgres:16.10-alpine3.22`, pinned by tag and verified
  by image digest in acceptance evidence. The candidate Compose project uses a
  private network, no published `5432`, a named external-to-Git data path,
  `768m` memory, `20` max connections, a healthcheck, and bounded shared
  memory.
- Prisma: `prisma`, `@prisma/client`, and `@prisma/adapter-pg` `7.9.1` with
  `pg` `8.22.0`, generated into a source-controlled ignored build directory.
  Prisma 7's `prisma.config.ts` configures the migration URL; runtime uses a
  `PrismaPg` adapter with `max: 5` and bounded connection acquisition.
- Passwords: `argon2` `0.45.1`, explicit Argon2id parameters
  `memoryCost=19456 KiB`, `timeCost=3`, `parallelism=1`, `hashLength=32`,
  `saltLength=16`. These are recorded in the hash string and tested without
  exposing hashes in logs or responses.
- Access tokens: `jose` `6.2.8`, HS256 using an external 32-byte signing
  secret, issuer and audience validation, 15-minute expiry, and claims only
  for `sub`, `sid`, `iss`, `aud`, `iat`, and `exp`.
- Validation: the existing pinned Zod `3.25.76`; no framework rewrite.
- Rate limits: `express-rate-limit` `8.6.1` with a process-local memory store,
  strict limits on login/registration/refresh and pairing operations, and
  redacted keys. A shared durable limiter is deferred until the deployment
  topology warrants it.
- Secrets: environment/runtime files outside Git. Invitation and refresh
  secrets use SHA-256 digests; six-digit pairing codes use keyed HMAC-SHA-256
  with an external pepper. Raw values are returned only at the explicitly
  documented one-time operator/device boundary and never persisted or logged.
- Backup encryption: age-compatible `age` CLI with an externally supplied
  passphrase in an ephemeral test environment. The repository provides a
  strict wrapper; no key or recipient is committed. OpenPGP or a cloud KMS is
  not introduced in P9.1.

## Data model

The initial schema contains only:

`User`, `PasswordCredential`, `AuthIdentity`, `Invitation`, `Session`,
`RefreshToken`, `Device`, `DevicePairing`, `UserSettings`, `DeviceSettings`,
and `AuditEvent`.

All IDs are UUIDs. User email is stored normalized and unique. PostgreSQL
timestamps are `timestamptz` through Prisma `DateTime`. Ownership foreign keys
are explicit. User-owned credentials and settings cascade with a user;
devices restrict deletion of their owner; device settings cascade with a
device; audit references are nullable and set null. No raw secret, password,
pairing code, token, audio, transcript, memory, chat, schedule, provider, or
future-phase record is stored.

Pairing status explicitly covers `ISSUED`, `CLAIMED`, `EXPIRED`, `REVOKED`,
`INVALIDATED`, and `FAILED`, because the locked P9.1 lifecycle requires these
states even though the preliminary schema used broader placeholders.

## Services and transactions

- `InvitationService`: operator-only create/revoke, one-time raw-secret
  display, expiry, atomic consume, and lifecycle audit.
- `AuthService`: email normalization, Argon2id verification, generic external
  failures, registration transaction, login rate-limit integration, and audit.
- `SessionService`: JWT issue/verify, opaque refresh hashing, rotation,
  replay-family revocation, current/all-session logout, and expiry handling.
- `UserService`: current-user projection and provider-neutral identity lookup.
- `DeviceService`: owned-device queries, settings ownership, default-device
  invariant, and unpair revocation.
- `PairingService`: challenge issuance/invalidation, bounded attempts, atomic
  claim, device credential hashing, expiry/revoke, and lifecycle audit.
- `SettingsService`: fixed Asia/Jakarta validation, safe ranges, Prudence-only
  voice profile resolution, and sanitized change audit.
- `AuditService`: allowlisted event types and metadata keys, immutable create
  only, and redaction tests.

Repositories are the only application code allowed to call Prisma. Sensitive
operations use one transaction for state mutation and audit insertion. Route
handlers perform parsing/authentication and translate typed errors to generic,
non-secret responses.

## API contract

All P9 routes are under `/api/v1` and are mounted only when `P9_ENABLED=true`:

```text
POST /api/v1/auth/register
POST /api/v1/auth/login
POST /api/v1/auth/refresh
POST /api/v1/auth/logout
POST /api/v1/auth/logout-all
GET  /api/v1/me

POST /api/v1/pairing/challenges
GET  /api/v1/pairing/:pairingId
POST /api/v1/pairing/:pairingId/claim
POST /api/v1/pairing/:pairingId/revoke

GET  /api/v1/devices
GET  /api/v1/devices/:deviceId
PATCH /api/v1/devices/:deviceId/settings
POST /api/v1/devices/:deviceId/unpair

GET  /api/v1/settings/user
PATCH /api/v1/settings/user
GET  /api/v1/settings/devices/:deviceId
PATCH /api/v1/settings/devices/:deviceId

GET /api/v1/ops/db/livez
GET /api/v1/ops/db/readyz
GET /api/v1/ops/db/migrations
```

The pairing claim request contains the authenticated user, pairing ID/code,
hardware ID, device name, and one device credential supplied at the pairing
boundary. The response contains a safe device summary and never the stored
credential. Mobile UX and copy are intentionally unspecified.

## Migration, backup, and restore

One reviewed initial migration creates the P9.1 schema from empty. Development
uses `prisma migrate dev` only to generate/review SQL; controlled environments
use `prisma migrate deploy`; startup never migrates and `db push`, reset, and
blind down migrations are prohibited. The acceptance harness applies the
migration to two empty databases, repeats deployment, compares schema output,
restarts the database, and checks for drift.

The backup wrapper creates a consistent `pg_dump` custom-format artifact,
atomically writes a timestamped `.dump`, emits a `.sha256`, encrypts the dump
with an external age passphrase, applies seven-daily/four-weekly retention,
and refuses unsafe permissions or missing secrets. Restore rehearsal decrypts
into a fresh private database, validates checksum, row counts, foreign keys,
hash-shaped credentials, lifecycle states, settings, and sanitized audits.
The local rehearsal is evidence only; off-VPS storage remains OPEN.

## Testing and resource gates

Tests are layered: pure unit tests for normalization, hashing, tokens,
rotation, lifecycle state machines, settings, and redaction; PostgreSQL
integration tests for migrations, registration, auth/session races,
ownership, pairing races, settings, readiness, restart persistence, and
backup/restore; security tests for injection, IDOR, malformed/expired/revoked
JWTs, rate limits, leakage, and concurrent claims; and the existing Backend
regression suite. Candidate PostgreSQL is bounded to 768 MiB/20 connections;
Prisma uses a pool of 5. Evidence records idle, migration, test, backup,
restore, and connection-test memory, CPU, disk/database size, restart count,
OOMKilled, kernel OOM delta, and host `MemAvailable` minimum.

## Rollback and open risks

Rollback disables P9 routes, restores the prior application image/config, and
keeps the candidate database volume for review. Database replacement is never
an automatic down migration; it requires an isolated verified restore and
explicit approval. Known residual risks are process-local rate-limit state,
the absence of production email/password reset, and incomplete disaster
recovery until an off-VPS destination/key boundary is approved.
