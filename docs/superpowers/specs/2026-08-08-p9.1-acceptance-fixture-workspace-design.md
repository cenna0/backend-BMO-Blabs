# P9.1 Acceptance Fixture Workspace Design

## Goal

Make the host acceptance fixture workspace self-provisioning and fail closed
without weakening the existing host/runtime state or password boundaries.

## Contract

`P9_ACCEPTANCE_STATE_FILE` remains the configurable absolute path to the host
fixture manifest. Its parent is the host acceptance workspace. The documented
default is `/tmp/p9-acceptance/fixture-state.json`.

The repository owns the workspace lifecycle. When `fixture:create` needs it
and the parent is absent, the host process creates the exact directory with
mode `0700`, then re-`lstat`s it. The expected host operator is
`bmo-admin:bmo-admin` (`1002:1002` on the acceptance host). An existing path
must already be a directory with that owner/group and exact protected mode;
the tooling never repairs an unsafe existing path with `chmod` or `chown`.

The only permitted child is `fixture-state.json`, a regular non-symlink file
owned by the host operator with mode `0600`. The file is schema-validated and
its synthetic identity is bound to its database and run ID. A valid pending or
completed manifest remains available for exact recovery. Unknown files,
symlinks, temporary-file residue, malformed manifests, and ambiguous state
fail closed. Cleanup unlinks only the exact validated manifest; it never
recursively removes the workspace, and the protected empty directory may
remain.

The workspace contains identifiers and cleanup-authorizing state only. It
never receives the canonical password, runtime password, database password,
password hash, access or refresh token, cookie, Authorization value, or
credential-bearing URL. Runtime state remains a container-local tmpfs file at
`/run/p9-acceptance/fixture-state.json`, and password handoff remains the
existing container-local tmpfs flow.

## Components and flow

`acceptance-workspace.ts` will own exact host-directory creation, metadata
validation, permitted-child validation, and exact-path cleanup primitives.
The helper will use native `lstat`/`mkdir`/directory-entry operations and
reject symlinks and non-directories. An absent-directory `EEXIST` race is
handled by revalidating the final path; no broad cleanup follows a failed
validation.

`acceptance-cli.ts` will call the helper after readiness and restored-target
identity proof and before writing the pending manifest. Stateful status,
cleanup, and run paths will validate the workspace boundary before using the
manifest. The existing atomic state-store write and runtime handoff remain in
place.

The resulting sequence is config preflight, evidence, runtime/readiness and
identity gates, protected workspace preparation, pending-manifest write,
mockable fixture worker invocation, returned-state validation, and only then
the later login runner. Workspace failure occurs before password read, worker
start, database connection, or fixture mutation.

## Error handling and cleanup

The helper reports one fail-closed acceptance-workspace error for unavailable,
unsafe, or ambiguous paths while retaining the underlying safety boundary.
It does not follow a substituted symlink, chmod/chown an existing path, or
delete unknown content. A valid current manifest is not overwritten by
`fixture:create`; the command requires explicit cleanup/recovery handling.
Worker failure removes only the exact pending manifest through the existing
validated state store and leaves the protected workspace in place. Cleanup
removes only the exact validated current-run manifest.

## Verification

Synthetic tests will cover absent creation, exact metadata, valid existing
workspaces, wrong type/owner/mode, symlinks, unexpected and temporary content,
valid and malformed/foreign state, atomic state writes, exact cleanup, worker
sequencing, failure before database mutation, state survival after worker
failure, and the clean-host `fixture:create` regression. Existing acceptance
runtime, Docker guard, loopback transport, readiness, wrapper, restore,
documentation, secret-scan, and full P9/backend verification will be rerun.
